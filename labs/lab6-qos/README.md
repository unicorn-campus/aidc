# lab6 QoS로 중요한 트래픽에 대역 보장하기

## 이 실습에서 배우는 것
- 길이 좁아져 패킷이 넘칠 때, 라우터가 "누구를 먼저 보낼지" 정하는 일을 QoS라고 함. 이 실습에서 직접 켜고 끄며 차이를 잼  
- QoS의 세 단계를 각각 다른 자리에서 봄: 분류(누구의 패킷인지 고름), 표시(번호표를 붙임), 큐(번호표대로 줄을 세움)  
- 같은 혼잡을 QoS 없이 한 번, QoS를 켜고 한 번 만들어 중요 트래픽이 받는 속도와 기다리는 시간을 비교함  
- lab1에서 한 OSPF를 그대로 쓰므로 길 찾기는 새로 배우지 않음. 이번에는 "길이 있는가"가 아니라 "막혔을 때 누가 참는가"를 봄  

### 왜 AI 데이터센터에서 QoS가 필요한가
GPU 서버끼리 학습 자료를 주고받는 망(RoCE)에서는 패킷이 몇 개만 버려져도 학습이 눈에 띄게 느려짐.  
그래서 실제 망은 아래 두 가지를 씀.  
- **PFC**: 받는 쪽이 보내는 쪽에 "잠깐 멈춰"라고 말해서 패킷을 버리지 않게 하는 방식  
- **DCQCN**: 혼잡 표시(ECN)를 본 보내는 쪽이 스스로 속도를 줄이는 방식  

### 이 실습이 진짜로 하는 것과 흉내 내는 것
| 주제 | 이 PC에서 |
|------|-----------|
| 분류, DSCP 표시, 줄 나누기(HTB), 대역 보장, 혼잡 속 지연 비교 | 직접 함(실제 명령과 실제 출력) |
| ECN(버리는 대신 혼잡 표시) | 직접 확인함. 단 TCP로 확인하며, 실제 RoCE는 RDMA라서 "같은 생각을 쓰는 다른 프로토콜"임 |
| PFC, DCQCN | **이 PC에서 할 수 없음.** 스위치 전용 칩과 장비가 필요하므로 이론과 시연으로만 다룸(확인 못 함) |
| 속도 숫자(10Mbit/s 등) | 교실에서 혼잡을 눈에 보이게 만들려고 정한 값임. 실제 100G, 400G 링크의 성능이 아님 |

lab5(Soft-RoCE)는 "RDMA가 어떻게 생겼나"를, 이 실습은 "그 RDMA가 타는 이더넷을 어떻게 지켜 주나"를 다룸.

## 구성도와 주소표
```text
   h1 10.60.1.10/24                              좁은 구간 10Mbit/s
   (중요 트래픽)                                 여기에 줄을 만듦
        |                                                |
      eth1                                               v
        |  10.60.1.0/24
   +----+----------------------+              +----------------------+
   |          r1               | eth3 ---- eth1 |        r2          |
   |  들어오는 쪽에서 표시      | 10.60.0.1/30  10.60.0.2/30          |
   |  나가는 쪽에서 줄 세우기   |              |                      |
   +----+----------------------+              +---------+------------+
        |  10.60.2.0/24                                 | eth2 10.60.3.1/24
      eth2                                              |
        |                                               |
   h2 10.60.2.10/24                              h3 10.60.3.10/24
   (대량 트래픽)                                 (받는 쪽, iperf3 서버)
```

| 장비 | 인터페이스 | 주소 | 역할 |
|------|-----------|------|------|
| h1 | eth1 | 10.60.1.10/24 | 중요 트래픽을 보내는 쪽 |
| h2 | eth1 | 10.60.2.10/24 | 대량 트래픽을 보내는 쪽 |
| h3 | eth1 | 10.60.3.10/24 | 받는 쪽. iperf3 서버 2개(5201 중요, 5202 대량) |
| r1 | eth1 | 10.60.1.1/24 | h1 쪽. 여기 들어오는 패킷에 표시를 붙임 |
| r1 | eth2 | 10.60.2.1/24 | h2 쪽. 여기 들어오는 패킷은 기본(0)으로 표시함 |
| r1 | eth3 | 10.60.0.1/30 | 좁은 구간. **나가는 쪽에 줄을 만듦** |
| r2 | eth1 | 10.60.0.2/30 | 좁은 구간 반대편 |
| r2 | eth2 | 10.60.3.1/24 | h3 쪽 |

- 컨테이너 이름은 `clab-lab6-r1`, `clab-lab6-r2`, `clab-lab6-h1`, `clab-lab6-h2`, `clab-lab6-h3`임  
- 이 실습은 `10.60.0.0/16` 안에서만 주소를 써서 다른 실습과 겹치지 않음  
- 길은 OSPF로 배움. 손으로 넣은 static 경로는 없음  

r1이 좁은 구간(eth3)에서 줄을 세우는 모양(QoS 켠 상태)은 아래와 같음.  
```text
   1:30  제어   표시 CS6(48)  보장 1Mbit  가장 먼저 내보냄(prio 0)   <- OSPF 대화
   1:10  중요   표시 EF (46)  보장 5Mbit  그다음(prio 1)            <- h1
   1:20  나머지 그 밖(기본 0) 보장 4Mbit  마지막(prio 2)            <- h2
   남는 대역은 서로 빌려 씀(최대 10Mbit까지). 버리지 않음
```

## 용어 풀이
| 용어 | 쉬운 말 |
|------|---------|
| QoS | 선이 좁아져 다 못 보낼 때 누구를 먼저, 얼마나 보낼지 미리 정해 두는 일 |
| 분류(classify) | 패킷을 보고 "누구 것인지" 가려내는 일. 여기서는 출발지 주소(h1인가 h2인가)로 가림 |
| 표시(mark) | 가려낸 패킷의 IP 머리에 번호표를 적는 일. 이 뒤의 장비는 주소가 아니라 번호표만 보면 됨 |
| DSCP | 패킷 머리에 붙이는 6비트 번호표. 라우터는 이 번호를 보고 어느 줄에 세울지 정함 |
| EF(46) | "급하고 중요함"을 뜻하는 DSCP 번호. 이 실습에서 h1의 패킷에 붙임. 머리의 TOS 바이트로는 `0xb8` |
| CS6(48) | 라우팅 대화처럼 망 자체를 움직이는 제어 패킷에 쓰는 번호. TOS 바이트로는 `0xc0`. FRR의 OSPF가 스스로 붙임 |
| TOS 바이트 | IP 머리의 한 칸. 앞 6비트가 DSCP이고 뒤 2비트가 ECN임. 그래서 tc에는 DSCP x 4 값을 적음 |
| 큐(줄) | 패킷이 내보내질 차례를 기다리는 줄. 줄이 하나면 먼저 온 순서대로 나감(FIFO) |
| tc | 리눅스에서 줄(큐)과 규칙을 만들고 보는 명령. 이 실습의 QoS는 모두 r1 안의 tc로 만듦 |
| HTB | 줄 여러 개에 대역을 나눠 주는 큐 방식. 줄마다 보장과 상한을 정함 |
| 보장(rate)과 상한(ceil) | 보장은 "최소한 이만큼은 받음"이고 상한은 "아무리 남아도 이만큼까지만 씀". 보장은 상한이 아니라서 남는 대역은 빌려 씀 |
| prio | 줄 사이의 우선순위. 숫자가 작을수록 먼저 내보냄 |
| 왕복 시간(RTT) | ping을 보내고 답이 돌아올 때까지 걸린 시간. 줄에서 오래 기다릴수록 길어짐 |
| ECN | 패킷을 버리는 대신 패킷에 "혼잡함" 표시를 해서 보내는 쪽이 스스로 속도를 줄이게 하는 방식 |
| iperf3 | 정해진 속도로 패킷을 보내고 받은 속도와 잃은 비율을 재는 도구 |
| UDP와 TCP | UDP는 잃어도 다시 보내지 않고 정해진 속도로 보내므로 혼잡을 만들기 좋음. TCP는 잃으면 속도를 줄임 |

2. 길을 OSPF로 배웠는지 확인함  
   ```bash
   docker exec clab-lab6-r1 vtysh -c "show ip ospf neighbor"
   ```
   이렇게 나오면 성공: 이웃 한 줄이 나오고 `Full/-`임(시간 값은 바뀔 수 있음)  
   ```text
   10.60.255.2       1 Full/-          12.918s           37.081s 10.60.0.2       eth3:10.60.0.1
   ```
   뜻: r1이 r2(10.60.255.2)를 OSPF 이웃으로 찾았음. 이 실습의 길은 모두 이 OSPF로 배운 것임  

3. QoS 없이 혼잡을 만들어 잼  
   ```bash
   bash cfg/measure.sh off
   ```
   이렇게 나오면 성공: 약 32초 뒤 결과표가 나오고 **중요(h1)의 받은 속도가 5보다 한참 낮음**.  
   강사 PC 실측은 아래와 같음(2번 쟀음. 둘 사이에 실습 환경을 껐다 다시 띄움)  
   | 항목 | 1회차 | 2회차 |
   |------|-------|-------|
   | 중요 보낸 속도 | 5 Mbit/s | 5 Mbit/s |
   | **중요 받은 속도** | **1.57 Mbit/s** | **0.86 Mbit/s** |
   | 중요 잃은 비율 | 68.58 % | 82.76 % |
   | **중요 쪽 왕복 시간 평균** | **992.9 ms** | **992.5 ms** |

   뜻: h1(중요)이 5Mbit/s, h2(대량)가 20Mbit/s를 동시에 보내면 합이 25Mbit/s라서 10Mbit/s 구간이 넘침.  
   줄이 하나뿐이라 중요 패킷도 대량 패킷과 섞여 같이 버려지고, 같은 줄에서 기다리므로 ping도 1초 가까이 걸림.  
   왕복 약 992ms는 계산과 맞음: 줄 1000개 x 1228바이트 x 8 / 10Mbit/s = 약 0.98초.  
   `measure.sh`는 중요 흐름을 먼저 띄우고 1초 뒤 대량을 띄움. 혼잡이 생긴 뒤에는 iperf3가 연결을 못 맺기 때문임  

4. 표시가 실제로 붙는지 봄(창 두 개)  
   ```bash
   # 창1: 받는 쪽 h3에서 도착하는 패킷의 머리를 잡음
   docker exec clab-lab6-h3 tcpdump -ni eth1 -v -c 4 icmp
   ```
   ```bash
   # 창2: 창1을 띄운 뒤 h1과 h2에서 ping을 보냄
   docker exec clab-lab6-h1 ping -c 3 10.60.3.10
   docker exec clab-lab6-h2 ping -c 3 10.60.3.10
   ```
   이렇게 나오면 성공: h1이 보낸 패킷에는 `tos 0xb8`(EF), h2가 보낸 패킷에는 `tos 0x0`이 보임  
   ```text
   IP (tos 0xb8, ttl 62, id 62430, offset 0, flags [DF], proto ICMP (1), length 84)
   ```
   뜻: r1이 들어오는 쪽에서 h1의 패킷에 EF 번호표를 붙였음. ping 답장은 받은 표시를 그대로 돌려 주므로 답장도 `tos 0xb8`로 보임.  
   표시를 붙인 규칙은 아래 명령으로 봄  
   ```bash
   docker exec clab-lab6-r1 tc filter show dev eth1 ingress
   ```
   ```text
   match 0a3c010a/ffffffff at 12                       <- 출발지 10.60.1.10 인가
     action order 1:  pedit action pipe keys 1
      key #0  at ipv4+0: val 00b80000 mask ff03ffff    <- TOS 바이트를 0xb8 로 바꿈
     action order 2: csum (iph) action pass            <- IP 머리 검사값 다시 계산
   ```
   뜻: 출발지가 10.60.1.10(h1)이면 TOS를 0xb8로 바꾸고 IP 머리 검사값을 다시 계산함(`cfg/mark.sh`가 건 규칙).  
   주소를 보는 곳은 여기 한 번뿐이고, 이 뒤의 장비는 주소가 아니라 표시만 보면 됨.  
   `csum`(검사값 다시 계산)과 `pedit` 뒤의 `pipe`(다음 동작으로 넘김)가 빠지면 표시한 패킷이 라우터에서 버려져 ping이 끊김  

5. QoS를 켬(줄을 하나에서 셋으로)  
   ```bash
   docker exec clab-lab6-r1 sh /root/shape.sh on
   ```
   이렇게 나오면 성공: 아래 한 줄이 나옴  
   ```text
   shape.sh: eth3 = 10mbit 좁은 구간, 줄 3개(제어 1Mbit / 중요 5Mbit / 나머지 4Mbit). QoS 있음
   ```
   뜻: 좁은 구간의 속도(10Mbit/s)는 그대로이고 줄만 하나에서 셋으로 늘어남. 속도까지 바꾸면 무엇 때문에 달라졌는지 말할 수 없으므로 일부러 줄만 바꿈.  
   어느 줄에 설지는 주소가 아니라 표시로 고름. 아래 명령으로 확인함  
   ```bash
   docker exec clab-lab6-r1 tc -s filter show dev eth3
   ```
   이렇게 나오면 성공: `match 00c00000/00fc0000`(CS6)과 `match 00b80000/00fc0000`(EF) 규칙이 보임(개수는 바뀔 수 있음)  
   ```text
   ... flowid 1:30 not_in_hw (rule hit 3 success 3)
     match 00c00000/00fc0000 at 0 (success 3 )
   ... flowid 1:10 not_in_hw (rule hit 0 success 0)
     match 00b80000/00fc0000 at 0 (success 0 )
   ```
   뜻: `00c00000/00fc0000`은 "TOS 바이트의 윗 6비트가 0xc0(CS6)인가"를 묻는 것이고 주소는 보지 않음.  
   `success 3`은 OSPF 패킷 3개가 이 규칙에 걸렸다는 뜻임. FRR의 OSPF가 스스로 CS6를 붙여 보낸다는 것을 실측으로 확인했음.  
   그래서 제어용 줄(1:30)을 따로 두어 가장 먼저 내보냄. 혼잡에 OSPF 대화가 휘말리지 않게 하기 위해서임  

6. 같은 혼잡을 QoS를 켠 채로 다시 잼  
   ```bash
   bash cfg/measure.sh on
   ```
   이렇게 나오면 성공: 약 32초 뒤 **중요(h1)가 5.00 Mbit/s를 잃지 않고 받고**, 왕복 시간이 1ms 아래임.  
   | 항목 | A) QoS 없음(3번) | B) QoS 켬 1회차 | B) QoS 켬 2회차 |
   |------|------------------|-----------------|-----------------|
   | 중요 받은 속도 | 0.86 ~ 1.57 Mbit/s | 5.00 Mbit/s | 5.00 Mbit/s |
   | 중요 잃은 비율 | 68.58 ~ 82.76 % | 0 % | 0 % |
   | 중요 쪽 왕복 시간 평균 | 약 992 ms | 0.365 ms | 0.670 ms |
   | 대량 받은 속도 | 8.82, 9.54 Mbit/s | 4.96 Mbit/s | 4.95 Mbit/s |
   | 대량 잃은 비율 | 55.87, 52.32 % | 75.22 % | 75.26 % |
   | 대량 쪽 왕복 시간 평균 | 약 992 ms | 150.1 ms | 152.2 ms |

   뜻: 중요 트래픽은 약속한 5Mbit/s를 그대로 받고 기다림도 거의 없음. 대신 대량 트래픽이 참음.  
   대량이 75%나 잃는 것은 정상임. 20Mbit/s를 보내는데 자기 몫이 4 ~ 5Mbit/s뿐이기 때문임.  
   측정 끝에 나오는 줄별 통계에서 "누가 참았는지"가 숫자로 보임(20초 쟀을 때 1회차, 핵심 줄만 옮김)  
   ```text
   class htb 1:10 parent 1:1 leaf 110: prio 1 rate 5Mbit ceil 10Mbit     <- 중요
    Sent 12940989 bytes 10450 pkt (dropped 0, overlimits 0 requeues 0)
   class htb 1:20 parent 1:1 leaf 120: prio 2 rate 4Mbit ceil 10Mbit     <- 나머지
    Sent 12811888 bytes 10335 pkt (dropped 31363, overlimits 2534 requeues 0)
   class htb 1:30 parent 1:1 leaf 130: prio 0 rate 1Mbit ceil 10Mbit     <- 제어(OSPF)
    Sent 246 bytes 3 pkt (dropped 0, overlimits 0 requeues 0)
   ```
   중요 줄(`1:10`)은 버린 것이 0개이고 나머지 줄(`1:20`)은 31,363개를 버렸음.  
   위 줄 나열의 `<-` 설명은 이 안내서가 덧붙인 것이며 실제 출력에는 없음  

7. 보장은 "최소한"이지 "이만큼만"이 아님을 앎(읽기만 하는 단계)  
   QoS를 켠 채 한쪽만 보내면 남는 대역을 빌려 쓴다는 것을 강사가 따로 잰 결과임. 수강생이 따라 칠 명령은 없음.  
   | 보내는 쪽 | 보낸 속도 | 받은 속도 | 설명 |
   |----------|----------|----------|------|
   | 대량만 | 20 Mbit/s | 9.72 Mbit/s | 보장은 4Mbit/s지만 중요 쪽이 쉬므로 10Mbit/s 가까이 씀 |
   | 중요만 | 9 Mbit/s | 9.00 Mbit/s | 보장 5Mbit/s를 넘어 9Mbit/s를 다 씀 |

   뜻: 보장(rate)은 하한이고, 상한(ceil)은 10Mbit/s임. 그래서 놀리는 대역은 아무도 못 쓰는 것이 아니라 필요한 쪽이 빌려 씀.  
   이 두 값은 `measure.sh`로는 재지 못하며 이 안내서를 쓰며 다시 돌려 보지 않았음  

8. 혼잡을 버리지 않고 표시로 알리는 ECN을 봄  
   ```bash
   bash cfg/measure.sh ecn
   ```
   이렇게 나오면 성공: 약 32초 뒤 끝의 줄 안쪽 큐 통계에 `qdisc red 120:`가 보이고 `marked`가 `early`보다 훨씬 큼  
   ```text
   qdisc red 120: parent 1:20 limit 400000b min 30000b max 90000b ecn
     marked 97 early 1 pdrop 0 other 0
   ```
   뜻: 이번에는 대량을 UDP 대신 TCP로 보내고 ECN을 켠 상태로 잼. 줄이 길어지면 `red`가 패킷을 버리는 대신 "혼잡함" 표시(`marked`)를 함.  
   TCP가 그 표시를 보고 스스로 속도를 줄여서 중요 흐름은 5.00 Mbit/s를 그대로 받고(잃은 비율 0 %), 대량 TCP는 재전송이 1회뿐이었음.  
   | 항목 | 1회차 | 2회차 |
   |------|-------|-------|
   | 중요 받은 속도 | 5.00 Mbit/s | 5.00 Mbit/s |
   | 대량(TCP) 받은 속도 | 5.04 Mbit/s | 5.05 Mbit/s |
   | 대량 TCP 재전송 | 1회 | 1회 |
   | red가 표시한 횟수(`marked`) | 97 | 100 |
   | red가 버린 개수(`early`) | 1 | 2 |

   같은 상황을 UDP로 하면 `marked`가 0 ~ 1에 그침. UDP는 "ECN을 쓰겠다"는 표시를 붙이지 않기 때문임(실측).  
   이것이 DCQCN의 바탕이 되는 생각임. 다만 실제 RoCE에서는 TCP가 아니라 RDMA가 이 표시에 반응하며, 그 부분은 이 PC에서 확인하지 못함  

9. 검사를 돌림  
   ```bash
   ./check.sh
   ```
   이렇게 나오면 성공: 항목 11개가 모두 `[통과]`이고 마지막 줄이 `결과: 모두 통과`임. 약 10 ~ 11초 걸림.  
   혼잡을 직접 약 8초 만들어 재므로 그동안 화면이 조용함. 항목 제목은 아래와 같음(제목만 옮김. `[통과]` 줄의 숫자는 돌릴 때마다 다름)  
   ```text
   1) 길을 OSPF로 배웠는가 (손으로 넣은 static이 아닌가)
   2) 들어오는 쪽에서 DSCP를 적는 규칙이 걸려 있는가 (분류와 표시)
   3) 좁은 구간 나가는 쪽에 줄이 3개 있는가 (HTB 클래스)
   4) 줄마다 보장 대역이 맞는가
   5) 줄 세우는 기준이 '표시'인가 (주소를 보고 있지 않은가)
   6) 혼잡을 만들어 잼 (약 10초 걸림)
   7) 중요 트래픽이 중요 줄로 갔는가
   8) 받는 쪽에 EF 표시가 그대로 도착했는가
   9) 좁은 구간이 실제로 넘쳤는가 (혼잡이 없으면 아래 검사가 뜻이 없음)
   10) 혼잡 속에서도 중요 흐름이 약속한 대역과 짧은 기다림을 받는가
   11) 라우팅 대화(OSPF)가 제어 줄로 따로 빠지는가
   ```
   뜻: 통신이 되는지가 아니라 "표시를 보고 줄을 세워 중요 트래픽에 대역을 보장하는가"까지 확인함.  
   하나라도 실패하면 종료 코드가 1, 모두 통과하면 0임. 검사하는 동안 줄을 새로 깔지 않음(깔면 고장이 저절로 고쳐져 못 잡기 때문)

- 고장 4에서 `check.sh`는 늘 대량 20Mbit/s로 혼잡을 만드므로 숫자로도 무너짐. "겉보기에 통과"는 `fault-demo.sh`가 얌전한 대량(4M)으로 한 번 따로 재서 보여 줌  

### 숫자만 보고 "맞다"고 하면 안 되는 이유
- **고장 3**: 중요 줄의 보장을 1Mbit로 잘못 적어도 숫자는 정상과 똑같이 나옴. 상한(ceil)이 10Mbit이고 중요 줄이 우선(prio 1)이라,  
  한가할 때는 남는 대역을 빌려 5Mbit/s가 나오기 때문임. 설정값을 눈으로 본 4번 항목만 잡음.  
  값을 잘못 적어도 한가할 때는 안 보이고, 진짜 모자랄 때만 드러남  
- **고장 5**: 받은 속도, 잃은 비율, 중요 줄에 들어간 패킷 수가 모두 정상과 구별되지 않음.  
  오직 "무엇을 보고 줄을 세우나"(5번)와 "받는 쪽에 표시가 도착했나"(8번)가 잡음.  
  장비가 10대면 10대에 주소를 다 적어야 하고 주소가 바뀌면 다 고쳐야 함. 그래서 경계에서 한 번 표시하고 뒤에서는 표시만 보는 것임  
- 고장 4도 같은 교훈임. 보내는 쪽이 얌전해서 안 막힌 것이지, 막혔을 때 지켜 주는 장치가 있는 것이 아님  

## 주의
- 속도와 시간 숫자는 모두 강사 PC에서 잰 값이며, 강의장 PC에서의 동작은 아직 확인하지 못함(미확인)  
- "10Mbit/s"는 혼잡을 보이려고 정한 값임. 실제 AI 데이터센터 링크는 100G, 400G급이라 이 숫자를 실제 성능으로 읽지 않음  
- `bash cfg/measure.sh`는 WSL의 실습 폴더에서 돌림(컨테이너 안이 아님). 한 번에 약 32초 걸리므로 기다림  
- 컨테이너 `h1`, `h2`, `h3` 안의 `tc`는 쓰지 않음. 그 이미지의 `tc`가 죽는 일이 있어 `tc`는 모두 `clab-lab6-r1` 안에서 돌림  
- 긴 시간 혼잡을 주었을 때 OSPF 이웃이 끊어지는지는 재지 않음(20초 동안은 끊기지 않았음)

## 정리
- QoS는 "막혔을 때 누구를 먼저 보낼지"를 미리 정하는 일이고, 분류, 표시, 큐 세 단계로 나뉨  
- 경계(r1 들어오는 쪽)에서 DSCP를 한 번 붙이고 뒤에서는 표시만 보고 줄을 세움  
- 같은 10Mbit/s에서 줄만 하나에서 셋으로 바꾸자 중요 트래픽이 0.86 ~ 1.57에서 5.00 Mbit/s로, 기다림이 약 992ms에서 1ms 아래로 달라졌음  
- 통신이 되거나 숫자가 맞는 것만으로는 부족함. `check.sh`는 "의도한 방식으로 동작하는가"를 봄  
- PFC와 DCQCN은 실제 장비가 필요하므로 이론으로 다루고, ECN의 생각만 이 PC에서 확인했음
