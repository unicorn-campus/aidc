# lab6 QoS 중요한 트래픽에 대역 보장하기 (넷니 작업 기록)

## 학습 목표 한 줄
"좁은 구간이 막혔을 때, 중요하다고 표시한 트래픽만 약속한 만큼(5Mbit/s)을 받고 기다리는 시간도 짧다"를
직접 재서 보이고, QoS를 끄면 그 약속이 깨지는 것을 같은 방법으로 보임

## 왜 이렇게 만들었나
- QoS는 "선이 좁아질 때 누구를 먼저 보낼지 정하는 일"임. 그래서 일부러 좁은 구간(10Mbit/s)을 만들고 그 위에 넘치는 양을 보냄
- QoS의 세 단계를 각각 다른 자리에서 보이게 나눔
  1. 분류(classify): r1이 어느 포트로 들어온 누구의 패킷인지 고름
  2. 표시(mark): 고른 패킷의 IP 머리에 DSCP를 적음. 이 뒤부터는 주소가 아니라 표시만 보면 됨
  3. 큐(queue): r1의 좁은 구간 나가는 쪽에서 DSCP별로 줄을 나누고 줄마다 보장 대역을 줌
- "QoS 없음"과 "QoS 있음"의 차이를 **줄이 하나냐 셋이냐**로만 둠. 속도(10Mbit/s)는 둘 다 같음.
  속도까지 같이 바꾸면 "무엇 때문에 달라졌는지" 말할 수 없음
- 라우팅은 lab1에서 한 OSPF를 그대로 씀. 손으로 넣은 static 경로는 없음.
  QoS가 주제이므로 라우팅 확인은 lab1 몫이고 여기서는 최소 설정만 함

## 구성도
```text
   h1 10.60.1.10/24                              좁은 구간 10Mbit/s
   (중요 트래픽)                                 여기에 줄을 만듦
        |                                                |
      eth1                                               |
        |  10.60.1.0/24                                  v
   +----+----------------------+              +----------------------+
   |          r1               | eth3 ---- eth1 |        r2          |
   |  들어오는 쪽에서 표시      |10.60.0.1/30  10.60.0.2/30           |
   |  나가는 쪽에서 줄 세우기   |              |                      |
   +----+----------------------+              +---------+------------+
        |  10.60.2.0/24                                 | eth2 10.60.3.1/24
      eth2                                              |
        |                                               |
   h2 10.60.2.10/24                              h3 10.60.3.10/24
   (대량 트래픽)                                 (받는 쪽, iperf3 서버)

   r1 eth3 나가는 쪽의 줄 (QoS 켠 상태)
     1:30  제어   DSCP CS6(48)  보장 1Mbit  먼저 내보냄(prio 0)   <- OSPF 대화
     1:10  중요   DSCP EF (46)  보장 5Mbit  그다음(prio 1)        <- h1
     1:20  나머지 그 밖(기본 0) 보장 4Mbit  마지막(prio 2)        <- h2
     남는 대역은 서로 빌려 씀(ceil 10Mbit). 버리지 않음
```

## 주소 계획표
> 관리 네트워크 `dcnet-mgmt`(172.30.30.0/24)와 겹치지 않음.
> 다른 실습이 쓰는 192.168.1 ~ 2.0/24(lab2), 10.0.0.0/24 루프백(lab2 ~ lab4), 10.10.10.0/24(lab3, lab4)와도 겹치지 않음.
> lab6는 `10.60.0.0/16` 안에서만 씀

| 장비 | 인터페이스 | 주소 | 역할 |
|------|-----------|------|------|
| h1 | eth1 | 10.60.1.10/24 | 중요 트래픽을 보내는 쪽. 기본 길은 10.60.1.1 |
| h2 | eth1 | 10.60.2.10/24 | 대량 트래픽을 보내는 쪽. 기본 길은 10.60.2.1 |

| r1 | lo | 10.60.255.1/32 | OSPF router-id |
| r1 | eth1 | 10.60.1.1/24 | h1 쪽. 여기 들어오는 패킷을 EF(46)로 표시 |
| r1 | eth2 | 10.60.2.1/24 | h2 쪽. 여기 들어오는 패킷을 기본(0)으로 표시 |

| r2 | lo | 10.60.255.2/32 | OSPF router-id |

## 재는 방법
```bash
bash cfg/measure.sh off   # A) QoS 없음
bash cfg/measure.sh on    # B) QoS 켬
bash cfg/measure.sh ecn   # C) 대량을 TCP로 바꿔 ECN 표시 확인
```
- 중요(h1): UDP 5Mbit/s. 좁은 구간이 10Mbit/s이므로 혼자면 다 지나가야 하는 양
- 대량(h2): UDP 20Mbit/s. 혼자서도 좁은 구간을 넘치게 하는 양
- 둘을 같이 보내면 들어오는 양이 25Mbit/s가 되어 혼잡이 생김
- 동시에 h1과 h2에서 ping 15번을 보내 기다린 시간(왕복 시간)을 함께 봄
- 한 번 재는 데 약 32초 걸림

### A) QoS 없음 (줄 1개, FIFO) 대 B) QoS 켬 (줄 3개)

| 항목 | A 1회차 | A 2회차 | B 1회차 | B 2회차 |
|------|---------|---------|---------|---------|
| 중요(EF) 보낸 속도 | 5 Mbit/s | 5 Mbit/s | 5 Mbit/s | 5 Mbit/s |
| **중요(EF) 받은 속도** | **1.57 Mbit/s** | **0.86 Mbit/s** | **5.00 Mbit/s** | **5.00 Mbit/s** |
| 중요(EF) 잃은 비율 | 68.58 % | 82.76 % | 0 % | 0 % |
| 대량(기본) 받은 속도 | 8.82 Mbit/s | 9.54 Mbit/s | 4.96 Mbit/s | 4.95 Mbit/s |
| 대량(기본) 잃은 비율 | 55.87 % | 52.32 % | 75.22 % | 75.26 % |
| **중요 쪽 왕복 시간 평균** | **992.9 ms** | **992.5 ms** | **0.365 ms** | **0.670 ms** |
| 대량 쪽 왕복 시간 평균 | 992.7 ms | 991.7 ms | 150.1 ms | 152.2 ms |

- A에서 중요 트래픽은 약속한 5Mbit/s의 **17 ~ 31%**밖에 받지 못하고, 왕복 시간은 1초 가까이 됨
- A의 왕복 시간 약 992ms는 계산과 맞음: 줄 길이 1000개 x 1228바이트 x 8 / 10Mbit/s = 약 0.98초
  ("버퍼가 커서 느려지는" 현상. 줄을 길게 잡는 것이 늘 좋은 것은 아님을 보이는 자리)
- B에서 중요 트래픽은 **5.00 Mbit/s를 하나도 잃지 않고** 받고, 왕복 시간은 1ms 아래임
- B에서 대량 트래픽이 많이 잃는 것은 정상임. 보낸 양(20Mbit/s)이 자기 몫(4 ~ 5Mbit/s)보다 훨씬 많기 때문임

### B에서 r1 eth3의 줄별 통계 (20초, 1회차)
```text
class htb 1:10 parent 1:1 leaf 110: prio 1 rate 5Mbit ceil 10Mbit     <- 중요
 Sent 12940989 bytes 10450 pkt (dropped 0, overlimits 0 requeues 0)
class htb 1:20 parent 1:1 leaf 120: prio 2 rate 4Mbit ceil 10Mbit     <- 나머지
 Sent 12811888 bytes 10335 pkt (dropped 31363, overlimits 2534 requeues 0)
class htb 1:30 parent 1:1 leaf 130: prio 0 rate 1Mbit ceil 10Mbit     <- 제어(OSPF)

```
- 중요 줄은 버린 것이 0개, 나머지 줄은 31,363개를 버림. "누가 참았는지"가 숫자로 보임

### 남는 대역을 빌려 쓰는지 (QoS 켠 상태에서 한쪽만 보낼 때)
| 보내는 쪽 | 보낸 속도 | 받은 속도 | 설명 |
|----------|----------|----------|------|
| 대량만 | 20 Mbit/s | 9.72 Mbit/s | 보장은 4Mbit/s지만 중요 쪽이 쉬므로 10Mbit/s 가까이 씀 |
| 중요만 | 9 Mbit/s | 9.00 Mbit/s | 보장 5Mbit/s를 넘어 9Mbit/s를 다 씀 |

- 보장(rate)은 "최소한 이만큼"이지 "이만큼만"이 아님을 보이는 자리임

### C) ECN (혼잡을 버리지 않고 표시로 알리기)
- 대량 쪽을 UDP 대신 **TCP**로 바꾸고, h2와 h3에서 `net.ipv4.tcp_ecn=1`로 ECN을 켠 상태임
- 나머지 줄(1:20)에 `red ... ecn`을 걸어 두었으므로, 줄이 길어지면 버리는 대신 패킷에 "혼잡" 표시를 함

| 항목 | 1회차 | 2회차 |
|------|-------|-------|
| 중요(EF) 받은 속도 | 5.00 Mbit/s (잃은 비율 0 %) | 5.00 Mbit/s (잃은 비율 0 %) |
| 대량(TCP) 받은 속도 | 5.04 Mbit/s | 5.05 Mbit/s |
| 대량 TCP 재전송 | 1회 | 1회 |
| **red의 ECN 표시 횟수(marked)** | **97** | **100** |
| red가 버린 개수(early) | 1 | 2 |

```text
qdisc red 120: parent 1:20 limit 400000b min 30000b max 90000b ecn
  marked 97 early 1 pdrop 0 other 0
```
- `marked`가 버린 개수보다 훨씬 많음. 즉 "버려서 알리는" 대신 "표시해서 알리는" 일이 실제로 일어남
- TCP가 그 표시를 보고 스스로 속도를 줄였으므로 재전송이 1회뿐임
- 같은 상황을 UDP로 하면 `marked`가 0 ~ 1에 그침. UDP는 ECN을 쓰겠다는 표시를 붙이지 않기 때문임(실측)

## 확인 명령과 정상일 때 출력
1. OSPF 이웃: `docker exec clab-lab6-r1 vtysh -c "show ip ospf neighbor"`
   ```text
   10.60.255.2       1 Full/-          12.918s           37.081s 10.60.0.2       eth3:10.60.0.1
   ```
2. 표시가 실제로 붙는지: `docker exec clab-lab6-h3 tcpdump -ni eth1 -v -c 4 icmp` 를 띄워 두고 h1에서 ping
   ```text
   IP (tos 0xb8, ttl 62, id 62430, offset 0, flags [DF], proto ICMP (1), length 84)
   ```
   - h1에서 보낸 것은 `tos 0xb8`(DSCP 46), h2에서 보낸 것은 `tos 0x0`임
   - ping 답장은 보낸 쪽 TOS를 그대로 되돌려 주므로 답장도 `tos 0xb8`로 보임
3. 줄 세우는 규칙이 "표시"를 보는지: `docker exec clab-lab6-r1 tc -s filter show dev eth3`
   ```text
   ... flowid 1:30 not_in_hw (rule hit 3 success 3)
     match 00c00000/00fc0000 at 0 (success 3 )
   ... flowid 1:10 not_in_hw (rule hit 0 success 0)
     match 00b80000/00fc0000 at 0 (success 0 )
   ```
   - `00c00000/00fc0000`은 "TOS 바이트의 윗 6비트가 0xc0(CS6)인가"를 보는 것임. 주소를 보지 않음
   - `success 3`은 OSPF 패킷 3개가 이 규칙에 걸렸다는 뜻임. **FRR의 OSPF가 CS6로 표시해 보냄을 실측으로 확인함**
4. 들어오는 쪽 표시 규칙: `docker exec clab-lab6-r1 tc filter show dev eth1 ingress`
   ```text
   match 0a3c010a/ffffffff at 12                       <- 출발지 10.60.1.10 인가
     action order 1:  pedit action pipe keys 1
      key #0  at ipv4+0: val 00b80000 mask ff03ffff    <- TOS 바이트를 0xb8 로 바꿈
     action order 2: csum (iph) action pass            <- IP 머리 검사값 다시 계산
   ```
5. 줄별 통계: `docker exec clab-lab6-r1 tc -s class show dev eth3`
6. 줄 안쪽 큐와 ECN 표시: `docker exec clab-lab6-r1 tc -s qdisc show dev eth3`

## 랩니 검사 항목 제안
> 괄호 안 JSON 경로는 모두 실측으로 확인함. `tc -j` 출력을 `jq`로 읽으면 됨.
> `tc`는 r1(FRR 이미지, iproute2 6.9.0) 안에서 실행함. 호스트 컨테이너의 낡은 `tc`는 쓰지 않음(아래 「막힌 점」 참조)

| # | 항목 | 확인 방법 | 기대값 | 틀렸을 때 의심할 것 |
|---|------|----------|--------|---------------------|
| 1 | OSPF로 길을 배웠는가 | `vtysh -c "show ip route 10.60.3.0/24 json"` on r1 | `protocol`=`ospf` | static을 손으로 넣음 |
| 2 | 들어오는 쪽 표시 규칙이 있는가 | r1 `tc filter show dev eth1 ingress` | `pedit`와 `csum` 두 줄 모두 있음 | `mark.sh`를 돌리지 않음 |
| 3 | 표시가 실제로 붙는가 | h1에서 ping 뒤 h3에서 `tcpdump -v` | `tos 0xb8` | `csum` 또는 `pipe` 빠짐 |
| 4 | 줄이 3개 만들어졌는가 | r1 `tc -j class show dev eth3` | `handle`이 `1:10`, `1:20`, `1:30` 모두 있음 | `shape.sh on`을 안 함 |
| 5 | 보장 대역이 맞는가 | 같은 출력의 `.rate` | `1:10`=625000(5Mbit), `1:20`=500000(4Mbit), `1:30`=125000(1Mbit) | 값을 바꿔 적음 |
| 6 | 표시를 보고 줄 세우는가 | r1 `tc -j filter show dev eth3` | `.options.match.value`=`b80000`인 규칙의 `flowid`=`1:10` | 편법 2 |
| 7 | **중요 줄로 갔는가** | r1 `tc -j -s class show dev eth3`의 `1:10` | `.stats.packets` > 0, `.stats.drops` = 0 | 표시가 안 붙음 |
| 8 | **중요 흐름이 보장 대역을 받는가** | `bash cfg/measure.sh on` | 받은 속도 >= 4 Mbit/s, 잃은 비율 <= 5 % | 4 ~ 7번부터 확인 |
| 9 | 중요 쪽 기다린 시간이 짧은가 | 같은 측정의 왕복 시간 | 중요 쪽 평균 <= 10 ms, 대량 쪽 평균 >= 50 ms | 중요 줄에 `fq_codel` 없음 |
| 10 | 제어 줄이 비어 있지 않은가 | r1 `tc -j -s class show dev eth3`의 `1:30` | 30초 뒤 `.stats.packets` >= 2 | CS6 필터를 안 걸음 |
| 11 | ECN이 표시로 알리는가 | ecn 측정 뒤 r1 `tc -j -s qdisc show` | `red`의 `.marked` >= 20, `.early` 초과 | `tcp_ecn` 확인 |

- **판정 기준 한 줄 요약**: `1:10` 클래스의 `.stats.packets` > 0 이고,
  `cfg/measure.sh on`의 중요 흐름 받은 속도가 4 Mbit/s 이상이며 잃은 비율이 5% 이하임
- 8번과 9번은 측정값이라 돌릴 때마다 조금씩 달라짐. 실측 범위는 중요 받은 속도 5.00, 왕복 시간 평균 0.365 ~ 0.670ms임
- A(QoS 없음) 쪽 값도 검사에 넣으면 좋음. 실측 범위는 중요 받은 속도 0.86 ~ 1.57 Mbit/s, 왕복 시간 평균 약 992ms임

### 편법 2: 표시를 지우고 출발지 주소로 줄 세우기
- 하는 법: `tc qdisc del dev eth1 clsact`로 표시 규칙을 지우고,
  eth3에 `tc filter ... u32 match ip src 10.60.1.10/32 flowid 1:10`을 검
- 결과(실측): 중요 받은 속도 5 Mbit/s, 잃은 비율 0 %. `1:10` 클래스에 패킷도 15,663개 들어감. **겉보기로는 통과**
- 들키는 곳: h3가 받는 패킷이 `tos 0x0`임(검사 3번). 필터가 `match 0a3c010a/ffffffff`로 주소를 봄(검사 6번)
- 수업에서 할 말: "장비 10대짜리면 10대에 주소를 다 적어야 하고, 주소가 바뀌면 다 고쳐야 함.
  그래서 경계에서 한 번 표시하고 뒤에서는 표시만 보는 것임"

### 편법 3: 보장을 주는 대신 대량 쪽 상한을 묶음 (제안, 실측 안 함)
- 하는 법: `1:20`의 `ceil`을 5mbit로 묶고 `1:10`의 보장을 지움
- 예상: 둘을 같이 보낼 때는 중요 쪽이 5Mbit/s를 받아 통과처럼 보임
- 들키는 곳: 대량만 혼자 보낼 때도 5Mbit/s밖에 못 씀(남는 대역을 못 빌림).
  정상일 때의 실측값은 9.72 Mbit/s임
- 이 항목은 돌려 보지 않음. **확인 못 함**

## 막힌 점과 해결 (모두 실측)
1. **IP 머리를 고치면 검사값(체크섬)을 다시 계산해야 함**
   - 증상: 표시 규칙을 건 뒤 h1에서 h3로 ping이 100% 안 됨. h2는 됨
   - 원인: `pedit`이 TOS 바이트만 바꾸고 IP 머리 검사값은 그대로 두어 라우터가 그 패킷을 버림.
     h2 쪽은 0을 0으로 바꾸는 셈이라 값이 안 변해서 멀쩡했음
   - 해결: `action csum ip`를 뒤에 붙임
2. **`pedit` 뒤에 `pipe`를 붙여야 다음 action이 돌아감**
   - 증상: `csum`을 붙였는데도 여전히 ping이 안 됨
   - 원인: tc action의 기본 끝맺음이 `pass`(여기서 끝)여서 `csum`이 한 번도 실행되지 않음.
     `tc -s filter show`의 `csum` 통계가 0패킷인 것으로 확인함
   - 해결: `action pedit ... pipe action csum ip pass`
3. **혼잡이 생긴 뒤에는 iperf3가 연결을 못 맺음**
   - 증상: 대량 흐름을 먼저 띄우고 1초 뒤 중요 흐름을 띄웠더니 중요 흐름이 0 Mbit/s로 나옴
   - 원인: iperf3는 측정 전에 제어용 TCP 연결을 먼저 맺는데, 그때 이미 왕복 시간이 1초에 가까워 실패함
   - 해결: `measure.sh`에서 중요 흐름을 먼저 띄우고 1초 뒤 대량 흐름을 띄움
4. **호스트 컨테이너의 `tc`가 죽음**
   - 증상: `ghcr.io/hellt/network-multitool`(iproute2 ss200330) 안에서 `tc -s qdisc show`가 Segmentation fault
   - 원인(추정): 낡은 iproute2가 새 커널(6.18)이 주는 통계 모양을 못 읽음. 원인은 끝까지 확인하지 않음
   - 해결: 큐와 통계는 모두 r1(FRR 10.2.1 이미지, iproute2 6.9.0) 안에서 봄. 호스트에서는 `tc`를 쓰지 않음
5. **OSPF 대화가 혼잡에 휘말릴까 걱정했으나 확인됨**
   - FRR의 ospfd가 보내는 패킷은 DSCP CS6(TOS 0xc0)로 나감. `tc -s filter show`의 `success` 수로 확인함
   - 그래서 제어용 줄(1:30)을 따로 두어 가장 먼저 내보냄. 실제 데이터센터도 같은 방식임

## 알아 둘 점
- HTB가 재는 양은 IP 패킷 길이이고 iperf3가 적는 속도는 UDP 속살 길이라 둘이 약 2 ~ 3% 다름.
  20초 동안 1:1 클래스가 내보낸 양이 약 26 ~ 30MB로 10Mbit/s보다 조금 많게 보이는 이유임
- 받은 속도는 iperf3가 적어 주는 "보낸 속도 x (1 - 잃은 비율)"로 계산함. `measure.sh`가 그 계산을 함
- 이 실습에서 쓴 "10Mbit/s"는 교실에서 혼잡을 눈에 보이게 만들기 위한 값임.
  실제 AI 데이터센터 링크는 100G, 400G급이며 여기서 잰 숫자를 실제 성능으로 읽으면 안 됨

## AI 데이터센터와의 연결 (교재에 밝힐 것)
- 실제 GPU 학습망(RoCE)은 **PFC**(Priority Flow Control, 상대에게 "잠깐 멈춰"라고 말해 패킷을 안 버리게 하는 방식)와
  **DCQCN**(ECN 표시를 보고 보내는 쪽이 속도를 줄이는 방식)을 씀
- PFC는 스위치 ASIC과 이더넷 흐름 제어 프레임이 필요하므로 **이 PC에서는 할 수 없음**. 이론과 시연으로만 다룸
- DCQCN의 바탕이 되는 **ECN 개념**은 이 실습의 C) 단계에서 실제로 확인함
  (`red ... ecn`이 버리는 대신 표시하고, TCP가 그 표시를 보고 속도를 줄임).
  다만 여기서 쓰는 것은 TCP이고 실제 RoCE는 RDMA이므로 "같은 생각을 쓰는 다른 프로토콜"이라고 밝혀야 함
- lab5(Soft-RoCE)와 이어서 설명하면 좋음: lab5는 "RDMA가 어떻게 생겼나", lab6는 "그 RDMA가 탈 이더넷을 어떻게 지켜 주나"

## 확인하지 못한 것
- 강의장 PC(강사 PC 아님)에서의 동작
- 편법 3(대량 쪽 상한만 묶기)은 제안만 했고 돌려 보지 않음
- `multitool` 이미지의 `tc`가 죽는 정확한 원인

- 실습 중 OSPF 이웃이 끊어지는지. A(QoS 없음)에서 20초 동안은 끊기지 않았으나,
  더 오래 혼잡을 주었을 때 어떻게 되는지는 재지 않음
- `check.sh`, `reset.sh`, `fault-demo.sh`는 랩니 담당이라 만들지 않음. 수강생용 `README.md`는 에듀니 담당

## 넷니 기준에서 바꾼 것
1. **9번을 "대량 쪽 왕복 시간 50 ms 이상"에서 "`1:20`이 버린 개수와 대량 잃은 비율"로 바꿈**
   - 이유: QoS를 켜면 대량 쪽 ping이 `1:20`에 섞여 73 % 넘게 버려짐.
     12번 보내도 하나도 안 돌아오는 일이 실제로 생김(실측 1회). 그러면 검사가 엉뚱하게 실패함
   - 버린 개수는 늘 남는 숫자라 흔들리지 않음. 대량 쪽 왕복 시간은 참고용으로 화면에만 적음
2. **ECN 항목(넷니 11번)은 `check.sh`에 넣지 않음**
   - 이유: ECN을 보려면 대량을 TCP로 바꿔 한 번 더 재야 해서 검사 시간이 두 배가 됨
   - ECN은 `sh cfg/measure.sh ecn`으로 따로 봄. 수업 흐름에서도 C) 단계로 따로 다룸
3. **재는 시간을 20초에서 8초로 줄임**
   - 이유: 검사 한 번이 1분을 넘지 않아야 함. 8초로도 정상과 고장의 숫자가 또렷이 갈림(아래 표)

## 고장 연습 실측 (전체 3회 돌려 같은 결과가 나옴. 마지막 1회는 지금 올라간 파일 그대로임)

| 1 | 들어오는 쪽 표시 규칙을 지움 | 통신 됨, 중요 2.0 ~ 2.5 Mbit/s, 왕복 72 ms | 2, 7, 8, 10 |

| 3 | 중요 줄 보장을 5Mbit 대신 1Mbit로 적음 | 통신 됨, **중요 5.00 Mbit/s, 잃은 비율 0 %** | **4번만** |

- 고장 2는 10번이 "받은 속도가 모자람" 또는 "잃은 비율이 큼" 중 하나로 걸림. 돌릴 때마다 다르나 같은 10번임
- **고장 3이 가장 무서운 자리임**: 숫자가 정상과 똑같음. `ceil`이 10Mbit이고 중요 줄이 우선(prio 1)이라

  수업에서 할 말: "값을 잘못 적어도 한가할 때는 안 보임. 진짜 모자랄 때만 드러남"
- **고장 5가 넷니의 편법 2임**: 받은 속도, 잃은 비율, 중요 줄 패킷 수가 정상과 구별되지 않음.
  오직 "무엇을 보고 줄을 세우나"(5번)와 "받는 쪽 표시"(8번)가 잡음
- 고장 4는 `check.sh`가 늘 대량 20Mbit/s로 혼잡을 만들기 때문에 숫자로도 무너짐.
  "겉보기 통과"는 `fault-demo.sh`가 얌전한 대량(4M)으로 한 번 재서 따로 보여 줌
