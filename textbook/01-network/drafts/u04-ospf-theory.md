## 1부. 라우팅이 왜 필요한가

### 2. 같은 망이면 바로, 다른 망이면 누군가 넘겨 줌
- 핵심: 컴퓨터는 보낼 곳이 "나와 같은 망"인지 먼저 따지고, 다르면 대신 넘겨 줄 장비에게 맡김
- 사실
  - 같은 망: 상대에게 직접 보냄
  - 다른 망: 내 쪽 출구 장비(기본 게이트웨이)에게 넘김. 그다음은 그 장비의 몫임
  - 넘겨받은 장비도 같은 판단을 반복함. 이 반복이 "라우팅"임
  - 넘길 곳을 고르는 규칙은 장비마다 표로 들고 있음(다음 장)
- 그림: 박스 3개를 가로로. [PC A] --같은 망--> [PC B], [PC A] --다른 망--> [라우터] --> [바깥]
- 근거: [RFC 1812 2.2.5.1 전달 규칙](https://www.rfc-editor.org/rfc/rfc1812)
- 강사용 메모
  - Q. 스위치와 라우터는 뭐가 다른가? A. U03에서 배운 스위치는 같은 망 안에서 전달함.  
    라우터는 망과 망 사이를 넘김. 요즘 장비는 둘을 한 상자에서 다 함
  - Q. 기본 게이트웨이를 모르면? A. 다른 망으로는 아무것도 못 보냄. 같은 망끼리만 통신됨

### 3. 같은 망인지 가르는 숫자: 프리픽스 길이
- 핵심: 주소 뒤의 `/24`, `/30`, `/32` 가 "어디까지가 같은 망인가"를 정함
- 사실
  - 주소는 32비트임. `/30`은 앞 30비트가 같으면 같은 망이라는 뜻임
  - `/30`은 주소 4개를 묶음. lab1의 `192.168.12.0/30`은 `.0 .1 .2 .3`임
  - lab1은 선 하나에 장비 2대만 붙으므로 `/30`을 씀
  - `/32`는 주소 하나뿐임. 장비의 대표 주소(루프백)에 씀. lab1의 `10.0.0.1/32`, `10.0.0.2/32`임
  - 오늘날 IP 주소 설계는 클래스(A, B, C)가 아니라 프리픽스 길이로 함
- 그림: 32칸 비트 막대 3개. `/24`는 앞 24칸 색칠, `/30`은 앞 30칸, `/32`는 32칸 전부 색칠
- 근거: [RFC 4632 CIDR](https://www.rfc-editor.org/rfc/rfc4632),  
  [lab1 주소표(README 구성도와 주소표)](https://containerlab.dev/manual/kinds/linux/)
- 강사용 메모
  - Q. `/30`에서 주소 4개 중 2개만 쓰는 이유는? A. 첫 주소와 마지막 주소는 망 자체와 전체 호출용으로 비워 둠
  - Q. `/31`은 못 쓰나? A. 장비끼리 잇는 선에는 쓰기도 함. 이 실습은 읽기 쉬운 `/30`으로 둠

### 4. 라우팅 표: 넘길 곳을 적어 둔 표
- 핵심: 장비마다 "어느 목적지는 어느 이웃에게 넘긴다"를 적은 표를 들고 있고, 그 표가 라우팅 표임
- 사실
  - 한 줄이 담는 것: 목적지 범위, 다음에 넘길 상대(다음 홉), 나가는 구멍(인터페이스), 출처, 거리, 메트릭
  - 표에 줄을 넣는 방법은 세 가지임
    - 직접 연결(connected): 내가 그 주소를 달고 있으니 저절로 생김
    - 손으로 넣음(static): 사람이 한 줄씩 적음
    - 프로토콜이 넣음(ospf, bgp 등): 이웃에게 배워서 생김
  - lab1에서 보는 것은 "직접 연결"과 "ospf"임. 고장 연습 5번에서만 "static"이 나옴
- 그림: 표 한 장을 크게 그리고, 각 칸에 말풍선으로 이름표를 붙임  
  (목적지 / 다음 홉 / 나가는 구멍 / 출처 / 거리 / 메트릭)
- 근거: [FRR zebra 문서](https://docs.frrouting.org/en/stable-10.2/zebra.html),  
  [ip-route(8) 매뉴얼](https://man7.org/linux/man-pages/man8/ip-route.8.html)
- 강사용 메모
  - Q. 표가 비면 어떻게 되나? A. 어디로 넘길지 몰라 버림. "네트워크에 도달할 수 없음"이 그 뜻임
  - Q. 표는 어디에 있나? A. 장비 메모리에 있음. 전원을 끄면 사라지고, 켜면 설정과 프로토콜로 다시 채워짐

### 5. 라우팅 표 한 줄 읽기 (lab1 실제 출력)
- 핵심: lab1에서 나오는 한 줄만 읽을 줄 알면 이 단원의 검사는 전부 읽을 수 있음
- 사실
  - 아래는 lab1 README 「따라 하기」 3단계의 실측 출력임
    ```text
    Routing entry for 10.0.0.2/32
      Known via "ospf", distance 110, metric 10, best
      * 192.168.12.2, via eth1, weight 1
    ```
  - `10.0.0.2/32`: 목적지. sw2의 대표 주소 하나
  - `Known via "ospf"`: 이 줄의 출처. 사람이 적은 것이 아니라 OSPF가 배워 온 것임
  - `distance 110`: 출처의 신뢰 순위. 숫자가 작을수록 먼저 뽑힘
  - `metric 10`: OSPF가 계산한 길의 비용 합
  - `* 192.168.12.2, via eth1`: 다음에 넘길 상대와 나가는 구멍
  - `best`: 같은 목적지로 가는 줄이 여럿일 때 실제로 쓰이는 줄이라는 뜻
- 그림: 위 출력 블록을 크게 띄우고 줄마다 화살표로 설명 라벨을 붙임
- 근거: [FRR zebra 문서](https://docs.frrouting.org/en/stable-10.2/zebra.html),  
  [RFC 2328 OSPF v2](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. `Known via "ospf"`가 `static`으로 보이면? A. 누군가 손으로 넣은 길임. lab1 검사 2번이 바로 이것을 봄
  - Q. 다음 홉이 비면? A. 직접 연결된 망이라는 뜻임. 넘길 상대 없이 바로 내보냄

### 6. 거리와 메트릭은 다른 것
- 핵심: 거리는 "누구 말을 믿을까", 메트릭은 "그 말 안에서 어느 길이 짧은가"임
- 사실
  - 거리(administrative distance): 출처끼리 비교할 때 씀. FRR 기준값임
    | 출처 | 거리 |
    |------|------|
    | 직접 연결(Connect) | 0 |
    | 손으로 넣음(Static) | 1 |
    | EBGP | 20 |
    | OSPF | 110 |
    | RIP | 120 |
    | IBGP | 200 |
  - 메트릭: 같은 출처 안에서 길끼리 비교할 때 씀. OSPF의 메트릭은 비용(cost) 합임
  - 중요한 결과: static(1)이 OSPF(110)보다 작음. 그래서 손으로 넣은 길이 OSPF 길을 밀어냄.  
    고장 연습 5번이 이 성질을 그대로 이용함
- 그림: 저울 두 개. 왼쪽 저울은 "출처 비교(거리)", 오른쪽 저울은 "길 비교(메트릭)"
- 근거: [FRR zebra 관리 거리 표](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. 왜 하필 110인가? A. 여러 제품이 오래 써 온 관행 값임. FRR 문서도 "다른 구현과 같은 값을 골랐다"고 밝힘
  - Q. 거리는 바꿀 수 있나? A. 바꿀 수 있음. 다만 바꾸면 검사와 실습의 전제가 흔들리므로 lab1에서는 손대지 않음

### 7. 줄이 여럿일 때 고르는 순서
- 핵심: 가장 자세한 줄이 먼저 이기고, 자세함이 같으면 거리, 거리도 같으면 메트릭으로 고름
- 사실
  - 1순위 가장 긴 프리픽스: `10.0.0.2/32`와 `10.0.0.0/8`이 함께 있으면 `/32`가 이김
  - 2순위 작은 거리: 같은 목적지에 static(1)과 OSPF(110)가 있으면 static이 이김
  - 3순위 작은 메트릭: 같은 OSPF 길이 둘이면 비용 합이 작은 쪽이 이김
  - 비용 합까지 같으면 길 두 개를 함께 씀(ECMP, 같은 비용 다중 경로). U05에서 본격적으로 다룸
- 그림: 깔때기 3단. 위에서 후보 줄 여러 개가 들어가 "긴 프리픽스 → 작은 거리 → 작은 메트릭" 순으로 걸러짐
- 근거: [RFC 1812 5.2.4.3 가장 긴 일치](https://www.rfc-editor.org/rfc/rfc1812),  
  [FRR zebra 관리 거리](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. 자세한 줄이 먼저인 이유는? A. 더 좁게 가리킨 줄이 그 주소를 더 잘 아는 줄이기 때문임
  - Q. ECMP는 몇 개까지 되나? A. 제품과 설정에 따라 다름. lab1은 선이 하나뿐이라 ECMP가 나오지 않음

## 2부. static 경로와 한계

### 8. static 경로: 사람이 직접 적음
- 핵심: static 경로는 "이 목적지는 저쪽으로 넘겨라"를 사람이 한 줄씩 적어 넣는 방식임
- 사실
  - lab1 고장 연습 5번에서 실제로 쓰는 명령은 아래임(`fault-demo.sh`)
    ```text
    ip route 10.0.0.2/32 192.168.12.2
    ```
  - 뜻: "10.0.0.2/32로 가려면 192.168.12.2에게 넘겨라"
  - 장점: 설정이 짧고, 적은 그대로 동작하며, 계산이 없어 예측하기 쉬움
  - 성질: 거리가 1이라 대부분의 프로토콜 경로를 밀어냄
- 그림: 사람 아이콘이 표에 줄 하나를 손으로 적어 넣는 그림
- 근거: [FRR zebra 정적 경로](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. static이 나쁜 설정인가? A. 아님. 자리에 맞으면 가장 좋은 선택임. 다음 장에서 자리를 구분함
  - Q. 적은 다음 홉이 꺼지면? A. 그 줄은 쓰이지 못하고 빠짐. 다만 다른 길을 스스로 찾아 주지는 않음

### 9. static이 맞는 자리와 안 맞는 자리
- 핵심: 길이 하나뿐이고 잘 바뀌지 않는 곳은 static, 길이 여럿이고 자주 바뀌는 곳은 동적 라우팅임
- 사실
  - static이 맞는 자리: 바깥으로 나가는 길이 하나뿐인 지점(기본 경로), 관리망처럼 거의 안 바뀌는 구간
  - static이 안 맞는 자리: 장비가 많고 길이 여러 갈래인 데이터센터 내부
  - 데이터센터 내부가 안 맞는 이유 두 가지
    - 줄 수가 장비 수를 따라 빠르게 늘어남(다음 장)
    - 선이 끊겨도 표가 스스로 바뀌지 않음
- 그림: 두 칸 비교 표. 왼쪽 "길 하나, 잘 안 바뀜 → static", 오른쪽 "길 여럿, 자주 바뀜 → 동적"
- 근거: [RFC 7938 2장 네트워크 설계 요구사항](https://www.rfc-editor.org/rfc/rfc7938)
- 강사용 메모
  - Q. 실무에서 static을 아예 안 쓰나? A. 씀. 기본 경로와 관리망은 지금도 static이 흔함
  - Q. 둘을 섞어도 되나? A. 됨. 다만 거리 때문에 static이 항상 이기므로 어디에 넣었는지 기록해 두어야 함

### 10. 장비가 늘면 손으로 못 함
- 핵심: 장비마다 모든 상대 주소를 적어야 하므로, 손으로 적는 줄 수가 장비 수의 제곱에 가깝게 늘어남
- 사실
  - 장비 n대가 서로의 대표 주소를 알아야 하면, 장비 한 대가 적을 줄은 n-1개임. 전체는 n × (n-1)개임
    | 장비 수 | 전체로 적어야 할 줄 수 |
    |---------|----------------------|
    | 2 | 2 |
    | 4 | 12 |
    | 10 | 90 |
    | 20 | 380 |
  - 위 숫자는 "각 장비가 다른 모든 장비의 대표 주소를 한 줄씩 적는다"는 가정에서 나온 계산임.  
    실제 설계에서는 주소를 묶어 줄 수를 줄이지만, 장비가 늘수록 늘어나는 성질은 같음
  - 더 큰 문제는 줄 수가 아니라 "선이 끊겼을 때 사람이 다시 적어야 함"임
- 그림: 왼쪽 장비 2대(선 2개 표시), 오른쪽 장비 10대(선이 빽빽하게 얽힌 모습). 아래에 줄 수 표
- 근거: [RFC 7938 2.3 운영비 최소화](https://www.rfc-editor.org/rfc/rfc7938)
- 강사용 메모
  - Q. 표의 숫자는 어디서 나온 것인가? A. RFC에서 가져온 숫자가 아니라 n × (n-1) 계산임. 슬라이드에도 계산식을 함께 둠
  - Q. 자동화 도구로 적으면 되지 않나? A. 적는 일은 자동화해도, 선이 끊긴 순간 1초 안에 바꾸는 일은 못 함

## 3부. 동적 라우팅의 생각

### 11. 동적 라우팅이 대신 해 주는 일 세 가지
- 핵심: 동적 라우팅은 이웃 찾기, 정보 나누기, 길 고르기를 장비가 알아서 반복함
- 사실
  - 이웃 찾기: 선 너머에 말이 통하는 상대가 있는지 주기적으로 확인함
  - 정보 나누기: 내가 아는 주소와 선을 이웃에게 알림. 이웃이 알려 준 것도 받아 둠
  - 길 고르기: 모은 정보로 목적지마다 가장 좋은 길을 계산해 라우팅 표에 심음
  - 선이 끊기면 세 가지가 다시 돌아 표가 저절로 바뀜. 이것이 static과의 결정적 차이임
- 그림: 원형 화살표 3단계(이웃 찾기 → 정보 나누기 → 길 고르기)가 계속 도는 그림
- 근거: [RFC 2328 OSPF v2](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 계속 돌면 장비가 바쁘지 않나? A. 평소에는 인사(Hello)만 오가 가벼움. 무거운 계산은 바뀐 순간에만 함
  - Q. 사람이 할 일이 없어지나? A. 아님. 무엇을 알릴지(설정)와 제대로 들어왔는지(검사)는 사람 몫임

### 12. 두 갈래: 거리 벡터와 링크 상태
- 핵심: 이웃이 알려 준 결론만 믿는 방식(거리 벡터)과 지도를 나눠 갖고 각자 계산하는 방식(링크 상태)이 있음
- 사실
  - 거리 벡터: "나는 저기까지 3걸음"처럼 결론만 주고받음. 대표적으로 RIP임
  - 링크 상태: "내 선은 이러이러함"이라는 조각을 모두에게 뿌리고, 각자 전체 지도를 만들어 계산함.  
    대표적으로 OSPF와 IS-IS임
  - 링크 상태의 장점: 모두가 같은 지도를 보므로 길이 꼬이는 일이 적고 수렴이 빠름
  - 링크 상태의 비용: 조각을 뿌리는 범위(영역) 안의 모든 장비가 계산을 다시 함
- 그림: 두 칸. 왼쪽은 이웃이 숫자만 건네는 그림, 오른쪽은 모두가 같은 지도를 들고 있는 그림
- 근거: [RFC 2328 1장과 2장](https://www.rfc-editor.org/rfc/rfc2328),  
  [RFC 7938 5.1 EBGP 선택 이유](https://www.rfc-editor.org/rfc/rfc7938)
- 강사용 메모
  - Q. 지도를 나눠 갖는다는 말이 어려움. A. 10장짜리 퍼즐을 각자 한 장씩 들고 서로 복사해 주는 모습임.  
    복사가 끝나면 모두 같은 10장을 갖게 됨
  - Q. RIP는 안 배우나? A. 이 과정에서는 비교용으로만 언급함. 데이터센터에서는 쓰지 않음

### 13. IGP와 EGP, 그리고 이 과정의 순서
- 핵심: 한 조직 안에서 쓰는 것이 IGP, 조직과 조직 사이에서 쓰는 것이 EGP임. OSPF는 IGP임
- 사실
  - IGP(Interior Gateway Protocol, 내부 게이트웨이 프로토콜): 한 관리 주체 안에서 씀. OSPF, IS-IS, RIP
  - EGP 자리의 실제 프로토콜은 BGP(Border Gateway Protocol, 경계 게이트웨이 프로토콜)임
  - 큰 데이터센터는 내부에서도 BGP를 쓰는 설계가 자리 잡음. 그 이유는 42장에서 다룸
  - 이 과정의 순서: U04에서 OSPF로 "길이 저절로 들어오는 것"을 보고, U05에서 BGP와 leaf-spine으로 넘어감
- 그림: 큰 원(한 조직) 안에 장비 여러 대와 "IGP" 라벨, 원과 원 사이 선에 "BGP" 라벨
- 근거: [RFC 7938 5.1](https://www.rfc-editor.org/rfc/rfc7938),  
  [RFC 2328 1장](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 그러면 OSPF는 안 쓰는 기술인가? A. 아님. 41장에서 다루듯 지금도 쓰이는 자리가 있음
  - Q. 왜 OSPF를 먼저 배우나? A. 이웃, 광고, 계산, 심기라는 네 동작이 가장 또렷하게 보이기 때문임

## 4부. OSPF

### 14. OSPF 한눈에 보기
- 핵심: OSPF는 각 장비가 자기 선 정보를 영역 전체에 뿌리고, 모두가 같은 지도로 최단 경로를 계산하는 방식임
- 사실
  - OSPF = Open Shortest Path First(공개된 최단 경로 우선). 표준은 RFC 2328(OSPF 버전 2)임
  - IP 위에서 직접 돎. IP 프로토콜 번호 89번임
  - Hello 패킷은 멀티캐스트 주소 224.0.0.5(AllSPFRouters)로 보냄
  - 최단 경로 계산에 다익스트라(Dijkstra) 알고리즘을 씀
  - lab1의 FRR 노드는 길을 고르는 일을 하므로 라우터라고도 부름. README는 "스위치"로 부름
- 그림: 가운데 "OSPF" 박스, 둘레에 네 조각(이웃, 광고, 지도, 계산)
- 근거: [RFC 2328 OSPF v2](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. "Open"이 무슨 뜻인가? A. 특정 회사 것이 아니라 공개 표준이라는 뜻임
  - Q. 번호 89는 어디에 쓰나? A. 방화벽에서 OSPF를 허용할 때 포트가 아니라 이 번호로 지정함

### 15. OSPF가 도는 다섯 단계
- 핵심: 이웃 찾기 → 알림 만들기 → 지도 맞추기 → 계산 → 표에 심기의 다섯 단계로 돎
- 사실
  - 1단계 이웃 찾기: Hello를 주고받아 양쪽이 서로를 보는지 확인함
  - 2단계 알림 만들기: 자기 선 정보를 LSA(Link State Advertisement, 링크 상태 광고)로 만듦
  - 3단계 지도 맞추기: 이웃과 LSA를 교환해 링크 상태 데이터베이스를 같게 만듦
  - 4단계 계산: 그 지도에서 자기를 뿌리로 하는 최단 경로 나무를 계산함(SPF)
  - 5단계 표에 심기: 계산 결과를 라우팅 표에 넣음. 이때 거리 110이 붙음
  - lab1 검사 3항목은 각각 1단계(이웃 Full), 5단계(출처가 ospf), 결과(통신)를 봄
- 그림: 가로 5단계 흐름도. 각 단계 아래에 lab1에서 그것을 보는 명령 이름을 작게 적음
- 근거: [RFC 2328 OSPF v2](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 다섯 단계가 매번 다 도나? A. 평소에는 1단계만 돎. 2 ~ 5단계는 무언가 바뀌었을 때만 다시 돎
  - Q. 어느 단계가 가장 자주 틀리나? A. 1단계임. 고장 연습 1 ~ 4번이 모두 1단계에서 깨짐

### 16. 1단계: Hello로 이웃을 찾음
- 핵심: 장비는 선마다 Hello를 주기적으로 보내고, 그 안에서 자기 이름이 보여야 양방향이 확인됨
- 사실
  - Hello 보내는 주기(HelloInterval): FRR 기본값 10초
  - 이웃이 끊겼다고 보는 시간(RouterDeadInterval): FRR 기본값 40초
  - RFC 2328은 랜 구간 Hello 예시 값을 10초로 들고, Dead는 Hello의 몇 배(예: 4배)로 두라고 적음
  - lab1 실측 출력의 `Dead Time 34.563s`는 40초에서 거꾸로 줄어드는 중임을 뜻함
    ```text
    Neighbor ID     Pri State           Up Time         Dead Time Address         Interface
    10.0.0.2          1 Full/-          15.436s           34.563s 192.168.12.2    eth1:192.168.12.1
    ```
- 그림: sw1과 sw2 사이에 Hello 화살표 양방향. 아래에 10초 눈금 타이머와 40초 눈금 타이머
- 근거: [RFC 2328 부록 C 인터페이스 파라미터](https://www.rfc-editor.org/rfc/rfc2328),  
  [FRR ospfd hello-interval과 dead-interval](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. Dead Time이 줄어드는 이유는? A. 남은 시간 표시임. Hello를 받을 때마다 40초로 다시 채워짐
  - Q. 10초가 너무 느리지 않나? A. 느림. 실무에서는 더 빠른 감지를 BFD 같은 별도 기능으로 함(U05 이후)

### 17. 이웃 상태가 Full까지 가는 길
- 핵심: 이웃은 Down에서 시작해 Full까지 단계를 밟고, Full이 되어야 길 정보가 완전히 맞은 것임
- 사실
  - 단계: Down → Init → 2-Way → ExStart → Exchange → Loading → Full
  - Init: 상대 Hello는 봤지만 그 안에 내 이름이 없어 양방향이 아직 아님
  - 2-Way: 상대 Hello 안에 내 이름이 보임. 양방향 확인됨
  - Exchange와 Loading: 서로 가진 지도 목록을 맞추고 모자란 조각을 요청해 받음
  - Full: 지도 조각을 완전히 맞춘 상태임. lab1 검사 1번이 보는 것이 이것임
  - lab1 출력의 `Full/-`에서 `-`는 "대표 장비(DR) 역할 없음"이라는 뜻임(26장 참고)
- 그림: 왼쪽에서 오른쪽으로 7칸 계단. Full 칸만 강조하고 아래에 "lab1 검사 1번" 라벨
- 근거: [RFC 2328 10.1 이웃 상태](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. Full이 아니면 어디부터 보나? A. 양쪽의 area 번호, Hello와 Dead 값, 선 주소가 같은 망인지 순서로 봄
  - Q. 2-Way에서 멈추면? A. 브로드캐스트 망에서는 정상일 수 있음. lab1은 point-to-point라 Full까지 가야 함

### 18. Hello에서 맞아야 하는 값
- 핵심: Hello 안의 값이 양쪽에서 하나라도 다르면 그 Hello는 버려지고 이웃이 맺어지지 않음
- 사실
  - 받은 Hello의 네트워크 마스크, HelloInterval, RouterDeadInterval을 자기 설정과 비교함.  
    하나라도 다르면 처리 중단하고 패킷을 버림
  - 예외: point-to-point 망과 가상 링크에서는 네트워크 마스크를 무시함
  - area 번호도 같아야 함. 다르면 이웃이 되지 않음
  - 이 성질이 고장 연습 3번(한쪽만 hello 5초)의 원인임
- 그림: Hello 패킷 상자 안에 네 칸(마스크, Hello, Dead, area). 한 칸만 색이 다르면 패킷에 X 표시
- 근거: [RFC 2328 10.5 Hello 수신 처리](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 한쪽만 바꿔도 양쪽이 다 끊기나? A. 결국 양쪽 다 끊김. 다만 먼저 실패로 보이는 쪽은 바꾼 쪽임.  
    반대쪽은 Dead 40초가 지나야 바뀜. lab1 고장 표의 "sw2 쪽이 먼저 실패"가 이 뜻임
  - Q. 자동으로 맞춰 주지 않나? A. 맞춰 주지 않음. 설정이 다르면 다른 망으로 보고 붙지 않음

### 19. 2단계: LSA로 내 선을 알림
- 핵심: 각 장비는 "내 인터페이스는 이렇게 생겼다"는 조각을 만들어 영역 전체에 퍼뜨림
- 사실
  - LSA = Link State Advertisement(링크 상태 광고). 장비 하나가 만드는 "내 선 정보 조각"임
  - LSA는 이웃에게만 주는 것이 아니라 영역 안 모든 장비에게 퍼짐(플러딩)
  - LSA에는 만든 장비 이름(라우터 ID), 선의 종류, 상대, 비용이 들어감
  - lab1에서 sw1이 만드는 조각에는 `10.0.0.1/32`와 `192.168.12.0/30`이 들어감.  
    `router ospf`의 `network` 문장이 "무엇을 넣을지"를 정함
- 그림: sw1 박스에서 종이 조각 하나가 나와 영역 전체로 복사되어 퍼지는 모습
- 근거: [RFC 2328 12장 LSA](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. `network` 문장이 하는 일이 정확히 뭔가? A. 두 가지임. 그 인터페이스에서 OSPF를 켜고,  
    그 주소를 LSA에 실어 알림. 둘이 함께 일어나므로 빼면 두 가지가 같이 사라짐
  - Q. 퍼뜨리면 정보가 새지 않나? A. 영역 밖으로는 그대로 나가지 않음. 영역을 나누는 이유 중 하나임

### 20. LSA 종류와 lab1이 쓰는 것
- 핵심: LSA는 역할별로 종류가 나뉘며, lab1처럼 영역 하나짜리 구성은 타입 1만 씀
- 사실
  - 타입 1 router-LSA: 장비가 자기 인터페이스 상태를 알림. 모든 장비가 만듦
  - 타입 2 network-LSA: 여러 장비가 붙은 망에서 대표 장비가 "여기 누가 붙어 있다"를 알림
  - 타입 3과 4 summary-LSA: 영역 경계 장비가 다른 영역의 길을 요약해 알림
  - 타입 5 AS-external-LSA: OSPF 바깥에서 들어온 길을 알림
  - lab1은 영역 하나(area 0)이고 point-to-point 선이라 타입 2가 생기지 않음. 타입 1만 오감
  - 타입 2와 타입 5라는 말은 U07 EVPN의 "타입 2 경로"와 이름만 같고 다른 것임. 섞이지 않게 함
- 그림: 5칸 표. lab1에서 쓰는 타입 1만 강조 색, 나머지는 흐리게
- 근거: [RFC 2328 표 15 LSA 종류](https://www.rfc-editor.org/rfc/rfc2328),  
  [RFC 5309 랜 위의 point-to-point 동작](https://www.rfc-editor.org/rfc/rfc5309)
- 강사용 메모
  - Q. EVPN 타입 2와 헷갈림. A. 여기 타입은 OSPF LSA 번호이고, EVPN 타입은 BGP 경로 번호임.  
    번호 체계가 아예 다름. U07에서 다시 짚음
  - Q. 타입 3 ~ 5는 안 배우나? A. 이 과정에서는 이름만 알고 넘어감. 영역이 하나뿐이라 lab1에서 볼 수 없음

### 21. 3단계: 지도를 똑같이 맞춤
- 핵심: 이웃끼리 가진 조각 목록을 비교하고 모자란 것을 요청해 받아, 영역 안 모두가 같은 지도를 갖게 됨
- 사실
  - 조각을 모아 둔 것이 링크 상태 데이터베이스(LSDB)임
  - 맞추는 순서: 목록 교환(Exchange) → 모자란 조각 요청(Loading) → 완료(Full)
  - 같은 영역 안 장비들의 LSDB는 같아야 함. 다르면 각자 다른 길을 계산해 통신이 꼬임
  - lab1에서 보는 명령은 `show ip ospf database`임.  
    실제 출력은 이 초안 작성 시 돌려 보지 않았으므로 "확인 못 함"으로 둠.  
    슬라이드에는 출력 대신 "강사가 수업 중 함께 띄워 보는 명령"으로 표시함
- 그림: sw1과 sw2가 각각 든 퍼즐판. 가운데 화살표를 지나면 두 판이 같아짐
- 근거: [RFC 2328 12.2 링크 상태 데이터베이스](https://www.rfc-editor.org/rfc/rfc2328),  
  [FRR ospfd show 명령](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. 조각이 영원히 남나? A. 아님. 오래되면 사라지므로 주기적으로 다시 만들어 퍼뜨림
  - Q. 수업에서 데이터베이스를 꼭 봐야 하나? A. 필수는 아님. 시간이 남으면 함께 띄워 보고, 없으면 넘겨도 됨

### 22. 4단계: SPF로 최단 경로를 계산함
- 핵심: 같은 지도를 놓고 각자 자기를 뿌리로 하는 최단 경로 나무를 계산함
- 사실
  - SPF = Shortest Path First(최단 경로 우선). 계산에 다익스트라 알고리즘을 씀
  - 장비마다 결과가 다름. 뿌리(자기 자신)가 다르기 때문임. 지도는 같아도 나무는 다름
  - "최단"의 기준은 거리나 속도가 아니라 비용(cost) 합임. 비용은 다음 장에서 다룸
  - 지도가 바뀌면 다시 계산함. 그래서 선이 끊겨도 사람이 손대지 않고 표가 바뀜
- 그림: 같은 지도 그림 두 개. 왼쪽은 sw1이 뿌리인 나무, 오른쪽은 sw2가 뿌리인 나무로 색칠
- 근거: [RFC 2328 16.1 영역 내 경로 계산](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 계산이 오래 걸리지 않나? A. 영역이 커질수록 늘어남. 그래서 영역을 나눠 범위를 줄임(25장)
  - Q. 모두 같은 결과가 나오나? A. 지도가 같으므로 "누가 어디로 가야 하는가"에 대한 판단은 어긋나지 않음

### 23. 5단계: 라우팅 표에 심음
- 핵심: 계산 결과가 라우팅 표에 들어가는 순간, 비로소 실제 통신에 쓰임
- 사실
  - 심을 때 출처는 `ospf`, 거리는 110, 메트릭은 비용 합이 됨
  - lab1 실측 출력에서 그대로 보임
    ```text
    Known via "ospf", distance 110, metric 10, best
    ```
  - 같은 목적지에 static(거리 1)이 있으면 OSPF 줄은 표에서 밀려남.  
    계산은 되었지만 쓰이지 않는 상태가 됨. 고장 연습 5번이 이 장면임
  - lab1 검사 2번은 이 단계의 결과를 봄. "경로가 있는가"가 아니라 "출처가 ospf인가"를 확인함
- 그림: SPF 계산 결과 상자에서 라우팅 표로 화살표. 표 옆에 거리 110 라벨
- 근거: [FRR zebra 관리 거리](https://docs.frrouting.org/en/stable-10.2/zebra.html),  
  [RFC 2328 11장 라우팅 테이블 구조](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 계산됐는데 표에 없으면? A. 거리가 더 작은 출처에 밀린 것임. 그 목적지의 다른 줄을 먼저 봄
  - Q. `best`는 무슨 뜻인가? A. 같은 목적지 후보 중 실제로 쓰이는 줄이라는 표시임

### 24. 비용(cost)은 어떻게 정해지나
- 핵심: 인터페이스마다 비용이 붙고, 길의 비용 합이 작은 쪽이 최단 경로가 됨
- 사실
  - FRR은 기준 대역폭(auto-cost reference-bandwidth)을 인터페이스 대역폭으로 나눠 비용을 냄
  - 기준 대역폭 기본값은 100Mbit/s임. 즉 100Mbit/s 이상인 선은 비용 1이 됨
  - 이 기준 값은 OSPF 도메인 안 모든 장비에서 같아야 함(FRR 문서 명시)
  - 인터페이스마다 `ip ospf cost`로 직접 정할 수도 있음
  - lab1 실측 출력의 메트릭은 10이었음. 즉 eth1 비용이 10으로 잡힘.  
    FRR이 이 가상 인터페이스의 대역폭을 몇으로 보았는지는 **확인 못 함**(FRR 문서에 기본 대역폭 값 표기 없음).  
    수업 중 `show ip ospf interface eth1`로 함께 확인할 것을 권함
- 그림: 선 3개에 각각 비용 1, 10, 100을 붙이고, 두 경로의 합을 비교하는 그림
- 근거: [FRR ospfd auto-cost reference-bandwidth](https://docs.frrouting.org/en/stable-10.2/ospfd.html),  
  [RFC 2328 부록 C 인터페이스 비용](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 빠른 선일수록 비용이 작은 이유는? A. 기준 값을 대역폭으로 나누기 때문임. 대역폭이 크면 몫이 작아짐
  - Q. 요즘 100Gbit/s 선도 비용 1인가? A. 기본 기준으로는 그렇게 됨. 그래서 실무에서는 기준 값을 올려 씀.  
    다만 한 대만 바꾸면 장비마다 계산이 어긋나므로 전부 같이 바꿔야 함

### 25. area 0: 영역을 나누는 이유
- 핵심: 영역은 지도를 뿌리는 범위이며, 모든 영역은 중심 영역인 area 0에 붙어야 함
- 사실
  - LSA는 영역 안에서만 퍼짐. 영역을 나누면 퍼지는 범위와 계산 범위가 줄어듦
  - 중심 영역(백본)의 번호는 0.0.0.0임. 보통 `area 0`으로 적음
  - 다른 영역은 area 0에 붙어야 함. 영역끼리 직접 붙을 수 없음
  - lab1은 장비 2대뿐이라 영역을 하나만 씀. 설정의 `area 0`이 그것임
    ```text
    router ospf
     ospf router-id 10.0.0.1
     network 10.0.0.1/32 area 0
     network 192.168.12.0/30 area 0
    ```
- 그림: 가운데 큰 원 "area 0", 양옆에 작은 원 "area 1", "area 2"가 중심 원에만 붙은 그림
- 근거: [RFC 2328 백본 영역 ID 0.0.0.0](https://www.rfc-editor.org/rfc/rfc2328),  
  [FRR ospfd network area 명령](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. 영역을 안 나누면 안 되나? A. 작으면 괜찮음. 커지면 LSA 퍼짐과 계산이 전체에 번져 부담이 됨
  - Q. `area 0`과 `area 0.0.0.0`은 다른가? A. 같음. 숫자로도 점 네 개 형식으로도 적을 수 있음

### 26. 네트워크 타입: broadcast와 point-to-point
- 핵심: 선에 장비가 둘뿐이면 대표 장비를 뽑을 필요가 없고, 그래서 lab1은 point-to-point로 지정함
- 사실
  - broadcast 타입: 여러 장비가 한 망에 붙은 경우를 가정함. 대표 장비(DR)와 예비(BDR)를 뽑음
  - DR을 뽑는 이유: 장비가 많을 때 모두가 서로 다 맺으면 관계 수가 폭증하기 때문임
  - point-to-point 타입: 상대가 하나뿐이므로 DR을 뽑지 않고 타입 2 network-LSA도 만들지 않음
  - lab1 설정에 `ip ospf network point-to-point`가 들어 있는 이유가 이것임
    ```text
    interface eth1
     ip address 192.168.12.1/30
     ip ospf network point-to-point
    ```
  - lab1 출력의 상태 `Full/-`에서 `-`는 DR 역할이 없다는 뜻임
  - FRR 문서는 point-to-point에서 인터페이스 주소가 `/32`면 번호 없는 링크로 다루며  
    `rp_filter`를 0으로 두라고 적음. lab1은 `/30`이라 이 경우에 해당하지 않음
- 그림: 두 칸. 왼쪽 broadcast(장비 4대와 가운데 DR 표시), 오른쪽 point-to-point(장비 2대, DR 없음)
- 근거: [RFC 5309 랜 위의 point-to-point 동작](https://www.rfc-editor.org/rfc/rfc5309),  
  [FRR ospfd ip ospf network](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. 지정하지 않으면 어떻게 되나? A. 이더넷 인터페이스는 broadcast로 다뤄져 DR 선출 과정이 들어감.  
    2대에서는 통신이 되더라도 불필요한 단계가 생김
  - Q. 양쪽 모두 지정해야 하나? A. 양쪽을 같게 두는 것이 안전함. lab1은 sw1과 sw2 모두 지정함

  - Q. 왜 containerlab을 설치하지 않았나? A. 이 PC는 다른 프로젝트 컨테이너가 Docker Desktop에서 돌고 있어서,

### 28. 토폴로지 파일 읽기
- 핵심: `lab1.clab.yml` 한 장이 "장비 몇 대를 어떤 이미지로 띄우고 어디를 이을지"를 전부 정함
- 사실
  - 실제 파일 내용
    ```yaml
    name: lab1

    mgmt:
      network: dcnet-mgmt
      ipv4-subnet: 172.30.30.0/24

    topology:
      kinds:
        linux:
          image: quay.io/frrouting/frr:10.2.1
      nodes:
        sw1:
          kind: linux
          binds:
            - cfg/daemons:/etc/frr/daemons
            - cfg/sw1.conf:/etc/frr/frr.conf
            - cfg/vtysh.conf:/etc/frr/vtysh.conf
      links:
        - endpoints: ["sw1:eth1", "sw2:eth1"]
    ```
  - `name: lab1`: 실습 이름. 컨테이너 이름이 `clab-lab1-`로 시작하는 이유임
  - `mgmt`: 관리 네트워크. 실습 통신과는 다른 통로임
  - `image`: 모든 노드가 쓸 컨테이너 이미지
  - `binds`: PC의 설정 파일을 컨테이너 안 경로에 연결함. 그래서 설정을 PC에서 고칠 수 있음
  - `links`: 가상 선. `sw1`의 eth1과 `sw2`의 eth1을 이음
  - 위 블록은 sw2 부분을 줄인 발췌임. sw2도 같은 모양으로 `cfg/sw2.conf`를 연결함
- 그림: YAML 블록을 왼쪽에, 오른쪽에 그 결과로 생긴 토폴로지 그림을 나란히
- 근거: [containerlab linux kind와 links 문법](https://containerlab.dev/manual/kinds/linux/)
- 강사용 메모
  - Q. eth0은 어디 갔나? A. 관리 네트워크용으로 자동으로 붙음. 실습 통신은 eth1로 함
  - Q. 설정을 고치면 바로 반영되나? A. 아님. `./reset.sh`로 다시 띄워야 함. 이것이 "되돌리기 한 줄"임

### 29. daemons 파일: 켤 기능만 켬
- 핵심: FRR은 기능마다 프로그램이 따로 있고, 이 파일이 무엇을 켤지 정함
- 사실
  - lab1이 켜는 것은 두 개뿐임
    ```text
    zebra=yes
    bgpd=no
    ospfd=yes
    ospf6d=no
    ```
  - `zebra`: 라우팅 표를 실제로 관리하고 커널에 심는 역할. 항상 켬
  - `ospfd`: OSPF를 담당. U04에서 켬
  - `bgpd=no`: U05에서 `yes`로 바뀜. 지금은 꺼 둠
  - 쓰지 않는 기능을 꺼 두면 메모리를 아끼고, 실수로 다른 프로토콜이 끼어드는 일을 막음
- 그림: 스위치 토글 목록 그림. zebra와 ospfd만 켜짐, 나머지는 꺼짐
- 근거: [FRR 기본 설정 문서](https://docs.frrouting.org/en/stable-10.2/basic.html),  
  [FRR zebra 문서](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. zebra를 끄면? A. OSPF가 계산을 해도 라우팅 표에 심지 못함. 통신이 안 됨
  - Q. 다 켜 두면 안 되나? A. 동작은 함. 다만 메모리를 더 쓰고, 어떤 프로토콜이 길을 넣었는지 추적이 어려워짐

    ```text
     ospf router-id 10.0.0.1
     network 10.0.0.1/32 area 0
     network 192.168.12.0/30 area 0
    !
    ```
  - `frr defaults datacenter`: 설정 기본값 묶음을 데이터센터용으로 고름.  
    FRR 문서는 이 묶음을 "한 관리 주체 안, 내부 링크에 공격적인 타이머를 쓰는 경우"로 설명함
  - `interface lo`: 장비 안 가상 구멍. 선이 끊겨도 꺼지지 않아 대표 주소로 씀
  - `interface eth1`: sw2와 이어지는 선. 주소와 네트워크 타입을 정함
  - `router ospf`: 여기부터 OSPF 설정임
  - `ospf router-id`: 이 장비의 OSPF 이름표. lab1은 루프백 주소와 같게 둠
  - `network ... area 0`: 어느 주소를 OSPF에 넣을지 정함. 두 줄이 각각 루프백과 선을 담당함
  - `!`는 주석 줄임. 설정을 읽기 좋게 나누는 표시임
  - sw2.conf는 주소만 다르고 모양이 같음(`10.0.0.2/32`, `192.168.12.2/30`, router-id `10.0.0.2`)
- 그림: 설정 블록 왼쪽, 오른쪽에 블록별 역할 라벨 4개(장비 이름 / 구멍 주소 / OSPF 켜기 / 알릴 주소)
- 근거: [FRR ospfd network area 명령](https://docs.frrouting.org/en/stable-10.2/ospfd.html),  
  [FRR 프로파일 설명](https://docs.frrouting.org/en/stable-10.2/basic.html)
- 강사용 메모
  - Q. `frr defaults datacenter`가 OSPF 타이머도 바꾸나? A. FRR 문서가 항목별로 밝히지 않아 **확인 못 함**.  
    다만 lab1 실측 출력의 Dead Time 34.563초는 기본값 40초와 맞음
  - Q. `network` 두 줄 중 하나를 빼면? A. 고장 연습 2번과 5번이 그 실험임. 빼는 줄에 따라 깨지는 곳이 달라짐

### 31. router-id와 루프백을 쓰는 이유
- 핵심: 장비 이름표(router-id)와 대표 주소(루프백)를 선과 무관하게 두면, 선이 끊겨도 신원이 흔들리지 않음
- 사실
  - router-id는 OSPF 안에서 장비를 가리키는 이름표임. IP 주소 모양이지만 통신 주소가 아님
  - lab1은 router-id를 루프백 주소와 같게 둠. 사람이 보기 쉽고, 장비마다 반드시 달라야 하기 때문임
  - lab1 출력의 `Neighbor ID 10.0.0.2`가 바로 sw2의 router-id임
  - 루프백은 물리 선에 묶이지 않음. 선 하나가 끊겨도 주소가 살아 있어 대표 주소로 적합함
  - 이 성질은 U05의 leaf-spine에서 더 중요해짐. 길이 여러 갈래여도 대표 주소는 하나로 유지됨
- 그림: 장비 박스 안에 루프백 동그라미 하나와 바깥으로 나가는 선 2개. 선 하나에 X 표시해도 동그라미는 그대로
- 근거: [RFC 2328 라우터 ID](https://www.rfc-editor.org/rfc/rfc2328),  
  [FRR ospfd router-id](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. router-id가 겹치면? A. OSPF가 혼란에 빠짐. 지도에서 두 장비가 한 장비로 보임
  - Q. 루프백에 꼭 `/32`를 써야 하나? A. 관행임. 주소 하나만 쓰므로 낭비가 없고 읽기도 쉬움

### 34. 단계 2: 이웃을 찾았는지 확인
- 핵심: 이웃이 Full이어야 길 정보가 오간 것이며, 아니면 뒤 단계는 볼 필요가 없음
- 사실
  - 명령
    ```bash
    docker exec clab-lab1-sw1 vtysh -c "show ip ospf neighbor"
    ```
  - 실측 출력
    ```text
    Neighbor ID     Pri State           Up Time         Dead Time Address         Interface
    10.0.0.2          1 Full/-          15.436s           34.563s 192.168.12.2    eth1:192.168.12.1
    ```
  - `Neighbor ID 10.0.0.2`: 상대의 router-id(31장)
  - `Full/-`: 지도를 완전히 맞춤. `-`는 DR 역할 없음(26장)
  - `Dead Time 34.563s`: 이 시간 안에 Hello가 오지 않으면 끊겼다고 봄(16장)
  - `Interface eth1:192.168.12.1`: 어느 구멍, 어느 주소로 맺었는지
  - 시간 값은 볼 때마다 달라짐. 모양이 같으면 정상임
- 그림: 출력 한 줄을 크게 쓰고 칸마다 설명 라벨
- 근거: [FRR ospfd show ip ospf neighbor](https://docs.frrouting.org/en/stable-10.2/ospfd.html),  
  [RFC 2328 10.1 이웃 상태](https://www.rfc-editor.org/rfc/rfc2328)
- 강사용 메모
  - Q. 아무 줄도 안 나오면? A. 이웃을 못 찾은 것임. 선, 주소, area, Hello 값 순으로 봄(18장)
  - Q. `vtysh`가 뭔가? A. FRR 장비 안에 들어가 상태를 보고 설정하는 명령 도구임

### 35. 단계 3과 4: 경로의 출처를 보고 통신을 확인
- 핵심: 통신이 되는지보다 "그 길이 어디서 왔는지"를 먼저 봄
- 사실
  - 경로 확인 명령
    ```bash
    docker exec clab-lab1-sw1 vtysh -c "show ip route 10.0.0.2/32"
    ```
  - 실측 출력
    ```text
    Routing entry for 10.0.0.2/32
      Known via "ospf", distance 110, metric 10, best
      * 192.168.12.2, via eth1, weight 1
    ```
  - 통신 확인 명령
    ```bash
    docker exec clab-lab1-sw1 ping -c 3 -I 10.0.0.1 10.0.0.2
    ```
  - 성공 기준: `3 packets transmitted, 3 packets received, 0% packet loss`
  - `-I 10.0.0.1`을 붙이는 이유: 보내는 주소를 루프백으로 고정해, 루프백끼리의 길이 양쪽 다 열렸는지 보기 위함임
  - `ospf` 자리에 `static`이 보이면 손으로 넣은 길임. 이 실습의 답이 아님
- 그림: 두 블록을 위아래로. 위 블록(경로)에 "먼저 봄", 아래 블록(ping)에 "그다음 봄" 라벨
- 근거: [FRR zebra 경로 출처와 거리](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. ping이 되면 된 것 아닌가? A. 아님. 이 단원의 목표는 OSPF로 길이 들어오게 만드는 것임.  
    통신만 살리는 방법은 여러 가지이고, 고장 연습 5번이 그 예임
  - Q. `-I`를 빼면? A. 보내는 주소가 eth1 주소로 잡힐 수 있어 루프백 경로를 확인하지 못할 수 있음

### 37. 고장 연습 돌리는 법
- 핵심: `fault-demo.sh`는 고장을 하나씩 내고 검사를 돌린 뒤 바로 원래대로 되돌림
- 사실
  - 명령
    ```bash
    ./fault-demo.sh
    ```
  - 동작 순서: 정상 상태 검사 → 고장 1 → 검사 → 복구 → 고장 2 → ... → 마지막에 복구 확인
  - 검사 결과가 바뀔 때까지 최대 60초를 기다린 뒤 검사를 돌림. 기다리는 이유는 Dead 40초 때문임
  - 마지막 `복구 확인`은 `결과: 모두 통과`로 끝남
  - 강사가 수업 전에 한 번 돌려 보면 어떤 화면이 나오는지 미리 익힐 수 있음
- 그림: 톱니 흐름도. 정상 → 고장 → 검사 → 복구를 다섯 번 반복하고 마지막에 복구 확인
- 근거: [FRR ospfd dead-interval 기본 40초](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. 수강생이 직접 돌려도 되나? A. 됨. 다만 몇 분 걸리므로 강사가 먼저 한 번 보여 주고 함께 읽는 편이 나음
  - Q. 중간에 멈추면? A. 고장이 남아 있을 수 있음. `./reset.sh`로 처음 상태로 되돌림

### 38. 고장 1부터 4까지 읽기
- 핵심: 네 가지 고장은 모두 "이웃이 맺어지지 않음"으로 끝나지만, 깨지는 자리가 서로 다름
- 사실
  - 아래 표는 2026-11-23 강사 PC에서 `fault-demo.sh`를 실제로 돌린 결과임(README 「고장 연습」)
    | 번호 | 일부러 내는 고장 | 실패로 잡힌 검사 | ping |
    |------|------------------|------------------|------|
    | 1 | sw1과 sw2 사이 선을 끊음 | 1번(sw1, sw2), 2번(sw1, sw2), 3번 | 안 됨 |
    | 2 | sw2가 선(192.168.12.0/30)을 OSPF에 넣지 않음 | 1번(sw2), 2번(sw2), 3번 | 안 됨 |
    | 3 | sw2의 hello 간격만 5초로 바꿈 | 1번(sw2), 2번(sw2), 3번 | 안 됨 |
    | 4 | sw2 선 주소를 오타 냄(192.168.12.2 를 192.168.13.2 로) | 1번(sw2), 2번(sw2), 3번 | 안 됨 |
  - 왜 깨지는가
    - 1번: 선이 없으니 Hello가 오가지 못함
    - 2번: `network` 문장이 빠지면 그 인터페이스에서 OSPF가 꺼짐. 알리지도 듣지도 않음
    - 3번: 받은 Hello의 HelloInterval이 자기 설정과 다르면 그 패킷을 버림(18장)
    - 4번: 주소가 `network 192.168.12.0/30` 범위 밖으로 나가 그 인터페이스에서 OSPF가 꺼짐.  
      동시에 양 끝이 서로 다른 망이 되어 직접 전달도 끊김
  - 2 ~ 4번에서 sw2가 먼저 실패로 잡히는 이유: sw1은 Dead 40초가 지나야 이웃을 내리기 때문임
- 그림: 4칸 카드. 카드마다 깨진 자리에 X 표시(선, network 문장, Hello 값, 주소)
- 근거: [RFC 2328 10.5 Hello 수신 처리](https://www.rfc-editor.org/rfc/rfc2328),  
  [FRR ospfd network area 동작](https://docs.frrouting.org/en/stable-10.2/ospfd.html)
- 강사용 메모
  - Q. 4번은 주소만 틀렸는데 OSPF까지 꺼지나? A. FRR 문서상 `network` 문장은 인터페이스 주소가  
    그 범위에 들어갈 때만 OSPF를 켬. 범위를 벗어나면 꺼짐
  - Q. 고장을 냈는데 검사가 바로 안 바뀜. A. 정상임. Dead 40초를 기다려야 바뀌는 경우가 있음

### 39. 고장 5: ping은 되는데 왜 실패인가
- 핵심: 손으로 넣은 static 경로로 통신만 살리면 ping은 되지만, 이 단원의 목표를 달성한 것이 아니므로 검사가 막음
- 사실
  - `fault-demo.sh`가 실제로 하는 일
    ```text
    router ospf
     no network 10.0.0.1/32 area 0
    ip route 10.0.0.2/32 192.168.12.2
    ```
  - 결과(README 고장 표 5번)
    - 검사 2번만 실패: "OSPF가 아니라 static으로 들어옴"
    - 검사 1번(이웃)은 통과: 선 주소는 그대로 OSPF에 들어 있어 이웃은 유지됨
    - ping은 됨
  - 왜 OSPF 경로가 밀려나는가: static의 거리가 1, OSPF가 110이라 static이 먼저 뽑힘(6장)
  - 그래서 검사 2번은 "경로가 있는가"가 아니라 "출처가 ospf인가"를 봄
  - 이 과정의 검사 원칙이 이 장면에 그대로 들어 있음: 통신 여부가 아니라 의도한 기술로 동작하는지를 봄
- 그림: 두 칸 비교. 왼쪽 "ping 결과: 성공"에 초록 표시, 오른쪽 "검사 2번: 실패"에 빨강 표시
- 근거: [FRR zebra 관리 거리(Static 1, OSPF 110)](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. 그래도 통신은 되는데 왜 문제인가? A. 선이 하나 더 생기거나 끊길 때 static은 따라가지 못함.  
    장비 수가 늘면 10장에서 본 문제가 그대로 돌아옴
  - Q. 실무에서도 이런 일이 생기나? A. 자주 생김. 급할 때 넣은 static을 지우지 않아 나중에 길이 꼬이는 사고가 흔함

## 8부. 데이터센터에서 OSPF의 자리

### 41. 언더레이와 오버레이, OSPF의 자리
- 핵심: 데이터센터 네트워크는 밑바닥 길(언더레이)과 그 위에 얹는 길(오버레이)로 나뉘며, OSPF는 밑바닥을 맡음
- 사실
  - 언더레이: 장비끼리 IP로 닿게 만드는 기본 망. 대표 주소(루프백)끼리 통하게 하는 것이 목표임
  - 오버레이: 언더레이 위에 터널을 얹어 가상 망을 만드는 층. U06의 VxLAN, U07의 EVPN이 여기에 해당함
  - 오버레이가 동작하려면 언더레이에서 루프백끼리 반드시 통해야 함
  - lab1에서 한 일이 바로 그것임: 루프백 `10.0.0.1`과 `10.0.0.2`가 서로 닿게 만듦
  - 즉 lab1은 뒤 실습 전부가 올라탈 바닥을 깐 것임
- 그림: 2층 구조. 아래층 "언더레이(루프백끼리 통함)", 위층 "오버레이(VxLAN, EVPN)" 점선 터널
- 근거: [RFC 7938 4.3 L3 전용 설계](https://www.rfc-editor.org/rfc/rfc7938)
- 강사용 메모
  - Q. lab1에서 오버레이를 못 보나? A. 못 봄. U06부터 봄. 지금은 바닥만 깐 단계임
  - Q. 언더레이는 꼭 OSPF여야 하나? A. 아님. BGP로도 함. 그 이야기가 다음 장임

### 42. 왜 큰 데이터센터는 BGP로 가나
- 핵심: 장비가 아주 많아지면 "지도를 전부에게 퍼뜨리는" 방식의 비용이 커져, BGP만 쓰는 설계가 자리 잡음
- 사실
  - RFC 7938은 서버 수만 대에서 10만 대 규모 데이터센터에서 BGP만 쓰는 설계 경험을 정리한 문서임
  - RFC 7938이 드는 이유(발췌)
    - BGP는 프로토콜 구조가 더 단순함. 이웃 유지와 흐름 제어를 TCP에 맡김
    - 정보 퍼짐의 양이 적음. BGP는 고른 최선 경로 하나만 전달함.  
      링크 상태 IGP는 고장이 나면 영역 전체로 사건이 퍼짐
    - AS 번호 배치와 경로 길이 검사로 원하지 않는 우회 경로를 막기 쉬움
  - 즉 OSPF가 틀려서가 아니라, 규모가 커지면 "모두가 같은 지도를 갖는" 성질의 비용이 커지기 때문임
  - U05에서 BGP와 leaf-spine으로 이어짐. 거기서 AS 번호 배치와 ECMP를 실제로 설정해 봄
- 그림: 왼쪽 "장비 수십 대: 지도 공유가 싸다", 오른쪽 "장비 수천 대: 퍼짐 범위가 부담"
- 근거: [RFC 7938 5.1 EBGP를 고른 이유](https://www.rfc-editor.org/rfc/rfc7938)
- 강사용 메모
  - Q. 그러면 OSPF를 배운 시간이 아까운가? A. 아님. 이웃, 광고, 계산, 심기라는 뼈대는 BGP도 같음.  
    U05에서 "이웃 상태"와 "경로 출처"를 보는 방식이 그대로 반복됨
  - Q. 어느 규모부터 BGP인가? A. 숫자로 딱 잘리지 않음. RFC 7938은 "대규모"를 서버 수만 대 이상으로 설명함

### 43. 정리와 다음 단원
- 핵심: 길이 저절로 들어오게 만들고, 그 길이 의도한 프로토콜로 들어왔는지 확인하는 습관을 가져가는 것이 U04의 결과임
- 사실
  - 오늘 설명할 수 있어야 하는 문장
    - 같은 망과 다른 망을 가르는 것은 프리픽스 길이임
    - 라우팅 표의 한 줄은 목적지, 다음 홉, 나가는 구멍, 출처, 거리, 메트릭으로 읽음
    - 거리는 출처끼리, 메트릭은 같은 출처 안에서 비교하는 숫자임. static 1, OSPF 110
    - OSPF는 Hello로 이웃을 찾고, LSA로 알리고, 같은 지도를 만들고, SPF로 계산해 표에 심음
    - `Known via "ospf"`가 아니라 `static`이면 이 실습의 답이 아님
  - 다음 단원 U05: BGP와 leaf-spine. 장비가 4대 이상으로 늘고, 같은 목적지로 가는 길이 여러 개가 됨
  - U05에서도 보는 방식은 같음: 이웃 상태를 보고, 경로 출처가 `bgp`인지 보고, 길이 몇 개인지 셈
- 그림: 왼쪽 U04 요약 카드 5장, 오른쪽에 U05 구성도 미리보기(leaf 2대와 spine 2대)
- 근거: [RFC 7938 Clos 토폴로지](https://www.rfc-editor.org/rfc/rfc7938),  
  [FRR zebra 관리 거리](https://docs.frrouting.org/en/stable-10.2/zebra.html)
- 강사용 메모
  - Q. 수강생이 OSPF 전부를 외워야 하나? A. 아님. 다섯 단계의 순서와 검사 세 항목을 읽을 수 있으면 됨
  - Q. 복습은 무엇으로? A. `./fault-demo.sh`를 다시 돌려 보고, 실패 항목만 보고 원인을 맞혀 보게 함

# 강사 참고 (슬라이드에 넣지 않음)

슬라이드에는 넣지 않되, 수강생 질문이 나왔을 때 강사가 답할 수 있게 모아 둠.

## A. DR과 BDR을 뽑는 과정
- 브로드캐스트 망에서 모든 장비가 서로 관계를 맺으면 관계 수가 장비 수의 제곱에 가깝게 늘어남.  
  그래서 대표(DR)와 예비(BDR)를 뽑고 나머지는 대표하고만 맺음
- 우선순위(Router Priority)가 높은 쪽이 대표가 되고, 같으면 router-id가 큰 쪽이 됨.  
  우선순위 0은 대표가 될 수 없음
- lab1은 point-to-point라 이 과정이 없음. 출력의 `Full/-`에서 `-`가 그 뜻임
- 근거: [RFC 2328 부록 C 라우터 우선순위](https://www.rfc-editor.org/rfc/rfc2328)

## B. LSA가 오래되면 어떻게 되나
- LSA에는 나이(LS age) 칸이 있고, 일정 시간이 지나면 만든 장비가 다시 만들어 퍼뜨림
- 같은 LSA 두 개가 들어오면 더 최근 것을 고름. 나이가 최대치인 것은 "지워라"라는 뜻으로 받아들임
- 근거: [RFC 2328 12.1.1 LS age](https://www.rfc-editor.org/rfc/rfc2328)

## C. network 문장 대신 인터페이스에서 켜는 방법
- FRR은 `router ospf`의 `network` 문장 대신 인터페이스에서 `ip ospf area AREA`로 켤 수도 있음
- 인터페이스가 아주 많으면 이 방식이 조금 빠르다고 FRR 문서가 적음
- 두 방식을 한 장비에서 섞는 것은 지원하지 않음. `ip ospf`가 있으면 `network` 명령이 실패함
- lab1은 읽기 쉬운 `network` 방식을 씀
- 근거: [FRR ospfd ip ospf area](https://docs.frrouting.org/en/stable-10.2/ospfd.html)

## D. 번호 없는 링크와 rp_filter
- FRR 문서는 point-to-point로 지정한 인터페이스 주소가 `/32`면 번호 없는 링크로 다루며,  
  이때 `net.ipv4.conf.<인터페이스>.rp_filter`를 0으로 두어야 멀티캐스트가 전달된다고 적음
- lab1은 `/30`을 쓰므로 이 경우에 해당하지 않음. U05의 BGP unnumbered에서 비슷한 주제가 다시 나옴
- 근거: [FRR ospfd ip ospf network](https://docs.frrouting.org/en/stable-10.2/ospfd.html)

## E. 기준 대역폭을 바꿀 때 주의
- `auto-cost reference-bandwidth` 기본값은 100Mbit/s이며, OSPF 도메인 안 모든 장비에서 같아야 함
- 한 대만 바꾸면 장비마다 다른 비용으로 계산해 길이 어긋남
- 근거: [FRR ospfd auto-cost reference-bandwidth](https://docs.frrouting.org/en/stable-10.2/ospfd.html)

## F. 영역 종류(스텁, NSSA)
- 영역은 바깥에서 들어온 길(타입 5 LSA)을 받을지에 따라 여러 종류로 나뉨
- lab1은 영역이 하나뿐이라 이 구분이 나타나지 않음. 이름만 알고 넘어가도 됨
- 근거: [RFC 2328 3.6 스텁 영역](https://www.rfc-editor.org/rfc/rfc2328)

## G. 인증
- OSPF는 패킷 인증을 지원함. FRR 문서는 단순 암호 방식이 안전하지 않다며 MD5 HMAC을 권함
- 데이터센터 내부 망에서도 이웃을 잘못 맺는 사고를 막는 데 쓰임. U04 실습에서는 설정하지 않음
- 근거: [FRR ospfd 인증 명령](https://docs.frrouting.org/en/stable-10.2/ospfd.html)

## H. 이 초안에서 확인하지 못한 것
| 항목 | 상태 | 비고 |
|------|------|------|
| eth1 비용이 10으로 잡힌 근거 | 확인 못 함 | FRR 문서에 기본 인터페이스 대역폭 값이 없음. `show ip ospf interface eth1`로 확인 필요 |
| `frr defaults datacenter`가 OSPF 타이머를 바꾸는지 | 확인 못 함 | FRR 문서가 프로파일별 항목을 나열하지 않음. 실측 Dead Time은 40초 기준과 맞음 |
| `show ip ospf database` 실제 출력 | 확인 못 함 | 이 초안 작성 시 실습을 띄우지 않음. 슬라이드에 출력 싣지 않음 |
| `show ip ospf interface eth1` 실제 출력 | 확인 못 함 | 위와 같음 |
